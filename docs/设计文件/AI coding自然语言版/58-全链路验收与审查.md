## 一、本阶段目标

| 维度 | 内容 |
|------|------|
| **产出** | 验收报告 + 14页面全量QA通过 + 安全审计通过 + Evals基线对比无劣化 |
| **Git分支** | `phase-7/ship`（从main切出） |
| **使用工具** | `/qa-only` `/cso` `run_evals` `/investigate` |
| **质量门禁** | 14页面无致命缺陷 + 安全审计无高危漏洞 + Evals劣化不超5% |

验收是阶段七的前半部分——用Gstack自动化工具对所有页面做全量QA、安全审计、Evals基线对比，修复发现的问题，打出 `v1.0.0-rc.1` 标签。

**为什么用自动化工具而不是手动验证？** 前六个阶段（文档42-57）我们通过 TDD 逐模块保证质量。验收阶段需要的是"广度检查"——覆盖全部14个页面、全量安全审计和Evals基线对比，而非深度审查单个模块。Gstack 的 `/qa-only` 用自动化遍历代替手动逐页检查，`/cso` 用自动化代替手动安全审计——速度快且不会遗漏。

## 三、开发流程

### Step 1: 创建分支 + 启动全栈 + `/qa-only`（全量浏览器验收）

**Git操作**（在Claude Code中输入）：

```
帮我在 main 基础上拉一条 phase-7/ship 分支，然后确认所有服务都跑起来了。
```

实际执行的命令等价于：`git checkout -b phase-7/ship main`

**启动全量QA**（在Claude Code中输入）：

```
/qa-only
```

`/qa-only` 是Gstack的纯自动化QA命令，区别于 `/qa`（交互式）。它会：

1. 逐一打开14个页面URL（`http://localhost:8000/teacher/chat` 等）
2. 检测：页面加载时间、控制台JS错误、UI元素缺失、按钮不可用、表单无法提交
3. 对可自动交互的元素执行点击/输入操作
4. 输出每页的交互通过率（目标 >= 90%）
5. 生成结构化QA报告，标注每个失败项的位置和截图
6. 自动生成验收清单 `acceptance-checklist.md`，按14个页面 + 全部API端点 + 三条用户旅程组织

**验收清单覆盖范围**（`/qa-only` 自动生成并填充）：

1. **14个页面逐一checklist**：
   - 教师端6个：Agent对话主页、出题工作台、学情面板、学生管理、障碍诊断、OCR批改
   - 学生端6个：登录页、AI对话页、练习页、错题本、复习页、个人报告页
   - 家长端2个：登录页、主面板（概览/学习报告/消息3个Tab）
   - 每个页面检查：页面加载、核心交互（按钮点击、表单提交）、空状态提示、错误状态处理、移动端适配

2. **全部API端点**（从 `backend/app/routers/` 目录自动扫描）：
   - 每个端点：正常200、未认证401、无效参数422、不存在资源404

3. **三条用户旅程**：
   - 教师：登录 -> 出题 -> 四维审核 -> 发布考试 -> 查看学情 -> 障碍诊断
   - 学生：登录 -> AI对话 -> 做练习 -> 查看错题本 -> 间隔复习 -> 个人报告
   - 家长：登录 -> 查看概览 -> 学习报告 -> 消息通知

**手动补充验证**（`/qa-only` 无法自动判断的交互，需手动确认，每个约1-2分钟）：

| 页面 | 手动验证点 | 为什么自动化不行 |
|------|-----------|----------------|
| Agent对话页 | SSE流式输出是否逐字显示、工具调用状态提示是否出现 | 流式内容的时序判断需要人眼确认 |
| 出题工作台 | `\ce{H2SO4}` 等化学公式是否渲染为可视化分子式而非LaTeX源码 | 公式渲染的正确性需要化学知识判断 |
| 学情面板 | Chart.js图表是否正常渲染（canvas不为空白）、3D散点图是否可拖拽旋转 | 图表内容正确性需要人工比对数据 |
| OCR批改 | 上传手写答题卡 -> 确认识别结果 + 自动评分的全链路 | 手写识别准确率需要人眼比对 |
| 学生练习页 | 提交答案后的即时反馈是否正确（正确显示绿色、错误显示红色+解析） | 反馈内容需要学科知识判断 |
| 错题本 | 错题解析中的化学公式是否正确渲染 | 同上 |

**视觉一致性检查**（`/qa-only` 报告内包含，无需单独命令）：

`/qa-only` 在遍历14个页面时会同步检查：
- **布局一致性**：三栏/两栏/居中布局是否和原型一致
- **颜色系统**：主色、辅助色、状态色（错误红/成功绿/警告橙）是否匹配 DESIGN.md（前端设计规范文件）
- **字体与间距**：标题/正文/辅助文字的字体大小和间距是否正确
- **组件状态**：按钮的 hover/active/disabled 状态、输入框的 focus/filled/error 状态
- **响应式**：手机尺寸（375x812，iPhone 14）下布局是否正确
- **关键元素**：图表配色、预警卡片颜色、状态标签样式

**`/qa-only` 报告你应重点关注**：
- 通过率 < 90% 的页面：必须修复后重新运行
- `Console errors > 0` 的页面：点开Console看具体错误，JS异常必须清零
- `Load time > 5s` 的页面：检查是否有阻塞的网络请求
- 视觉差异项：对照 DESIGN.md 确认是否为预期变更

**记录所有问题**到 `acceptance-checklist.md`，每条标注来源（`/qa-only` 或手动）和严重程度。

**如果出错**：

| 错误 | 原因 | 解决 |
|------|------|------|
| `/qa-only` 命令不可用 | Gstack 技能包未安装 | 回到文档42安装 Gstack；或用手动浏览器打开14个页面的 URL 逐页验证替代 |
| 页面加载超时（多个页面 > 10s 无响应） | 后端 API 未启动或 8000 端口未监听 | `curl http://localhost:8000/health` 确认后端存活；若未启动则 `uvicorn app.main:app --port 8000`；检查 SQLite 数据库文件 `chemai.db` 是否存在 |
| 交互通过率低于 90% | 前端组件存在未处理的 JavaScript 异常或 API 调用失败 | 打开浏览器 DevTools Console 逐页检查红色报错；优先修复导致按钮/表单不可用的 JS 错误；修复后重新运行 `/qa-only` |
| 控制台有 JavaScript 错误 | 前端构建产物与后端 API 版本不匹配、或静态资源 404 | 重新构建前端 `npm run build`；确认 `frontend/dist/assets/` 下所有 JS/CSS 文件可访问 |
| SSE 流式输出验证失败 | Agent 对话页的 EventSource 连接中断或后端未正确发送 `text/event-stream` | 检查后端 `/api/agent/chat` 端点是否返回 `Content-Type: text/event-stream`；确认前端 `EventSource` 未因 CORS 被拦截 |
| `fatal: 'main' is not a valid branch name` | 仓库尚未创建 main 分支，只有 master 或其他默认分支 | `git branch -a` 查看现有分支；若用 master：`git checkout -b phase-7/ship master`；或先 `git checkout -b main` 创建 main |
| Docker 服务启动失败（端口冲突） | 8000 端口被其他进程占用 | `netstat -ano \| findstr :8000` 找到 PID，`taskkill /PID <pid>` 终止；或修改 docker-compose.yml 端口映射 |

### Step 2: `/cso`（安全审计）

**操作**（在Claude Code中输入）：

```
/cso
```

`/cso` 是Gstack的安全审计命令（Code Security Overview），对项目进行全量安全检查：

1. **依赖漏洞扫描**：检查 `requirements.txt` 和 `package.json` 中的依赖是否存在已知CVE漏洞
2. **认证与授权审查**：验证JWT token生成/验证逻辑、权限矩阵的覆盖完整度、API端点的认证中间件
3. **注入风险检查**：SQL注入（SQLAlchemy ORM使用是否安全）、XSS（前端输入渲染是否转义）、命令注入
4. **密钥与配置审计**：检查 `.env` 文件是否被提交到Git、SECRET_KEY 强度、LLM API Key 是否硬编码
5. **数据安全**：敏感数据（密码、学生成绩、诊断报告）是否加密存储、日志中是否泄露个人信息
6. **依赖链安全**：检查第三方库的供应链风险

**输出**：结构化安全审计报告 `reports/security-audit-report.md`，包含：
- 发现的漏洞列表（按 CVSS 评分排序：严重/高/中/低）
- 每个漏洞的影响路径和修复建议
- 整体安全评分（A/B/C/D/F）

**安全审计通过标准**：
- 无严重（Critical）漏洞
- 无高危（High）漏洞
- 中危（Medium）漏洞若有，需在修复阶段全部处理
- 低危（Low）漏洞记录为已知问题，不阻断发布

**如果出错**：

| 错误 | 原因 | 解决 |
|------|------|------|
| `/cso` 命令不可用 | Gstack 技能包未安装或版本过低 | 更新 Gstack 到最新版；或手动执行 `pip-audit` / `npm audit` + 手动审查认证逻辑 |
| 依赖扫描发现高危 CVE | 使用了存在已知漏洞的第三方包版本 | 按报告建议升级依赖版本；`pip install --upgrade <package>` / `npm update <package>`；升级后重新运行测试确认无回归 |
| JWT 认证审计不通过 | token 有效期过长、未使用 refresh token 机制、密钥强度不足 | 缩短 token 有效期（建议 7200 秒）、增加 refresh token 轮换逻辑、使用 `openssl rand -hex 32` 生成强密钥 |
| `.env` 文件被 Git 跟踪 | 未在 `.gitignore` 中添加 `.env` | `git rm --cached .env` 移除跟踪；确认 `.gitignore` 包含 `.env` 行；重新生成新的 SECRET_KEY |
| 敏感数据未加密存储 | 数据库中直接存明文密码或 PII | 密码使用 `bcrypt` 哈希；PII 字段使用 AES-256 加密后存储；迁移已有数据 |

### Step 3: `run_evals --tier all --compare baseline.json`（Evals基线对比）

这是验收阶段最关键的质量门禁——确认前六个阶段的所有修改没有导致整体质量退化。

**操作**（在Claude Code中输入）：

```
run_evals --tier all --compare baseline.json
```

**三层评测全部运行**：

| 层级 | 内容 | 通过标准 |
|------|------|:------:|
| L1 单元 | 纯函数逻辑（规则引擎、置信度、状态机） | >= 95% |
| L2 集成 | API端点行为（结构、状态码、认证） | >= 90% |
| L3 质量 | AI内容质量（科学性、诊断准确率、辅导安全性） | >= 70% |

**决策树**：

```
run_evals --tier all --compare baseline.json
  │
  ├── 无劣化 或 劣化 <= 3%
  │   正常波动，记录到验收报告，继续。
  │
  ├── 劣化 3-5%
  │   需要处理：
  │   /investigate → 定位失败的Evals样本（如 golden_031、golden_077）
  │   → 修复代码 → git commit -m "fix(golden-NNN): [问题描述]"
  │   → 重新 run_evals --tier all --compare baseline.json
  │
  └── 劣化 > 5%
      严重退化，优先回退：
      /investigate → 定位bad commit
      → git revert <bad-commit>
      → 重新 run_evals
      或选择方案B：直接修复 → git commit → 重新 run_evals
```

**决策原则**：
- 3%以下：直接过，不做无意义的微调（过度优化可能导致过拟合）
- 3-5%：定位到具体样本修复，不能"改阈值凑数"
- 5%以上：revert优先——大范围劣化通常意味着某个commit有问题，逐个revert比逐个修快

**如果出错**：

| 错误 | 原因 | 解决 |
|------|------|------|
| `run_evals` 命令不可用（`command not found`） | Evals 工具链未安装 | 确认文档43已创建 `scripts/run_evals.py`；如文件丢失，让 Claude Code 重新创建（见文档43的 run_evals 轻量版步骤） |
| `baseline.json` 不存在（`FileNotFoundError`） | 首次运行 Evals 前未保存基线文件 | 回到文档52的 CLI 运行器部分，执行 `run_evals --tier all --save-baseline` 生成基线；如果是首次运行无需 `--compare` 参数 |
| 劣化 3-5% 需要定位但 `/investigate` 不可用 | Gstack investigate 命令未安装 | 手动定位：`git log --oneline` 查看近期 commits -> `git diff <commit>~ <commit>` 对比变更 -> 运行 `pytest evals/ -k "golden_031 or golden_077"` 确认失败样本 |
| 劣化超过 5%（严重退化）需回滚 | 某个近期 commit 引入了大范围 breakage | `git log --oneline -20` 列出最近 20 个 commit -> `git revert <bad-commit>` 逐一回退 -> 每次 revert 后 `run_evals --tier all --compare baseline.json` 确认恢复；方案B：直接定位修复代码后重新 run_evals |

### Step 4: 修复发现的问题

**汇总问题清单**：将 Step 1-3 发现的所有问题汇总，按严重程度排序：

| 严重度 | 定义 | 是否阻断发布 |
|--------|------|:----------:|
| 严重 | Agent无法回复、页面白屏、数据丢失、安全审计Critical漏洞 | 是 |
| 高 | 核心功能异常、API返回500、公式不渲染、安全审计High漏洞 | 是 |
| 中 | UI错位、移动端适配问题、非核心功能异常、安全审计Medium漏洞 | 否 |
| 低 | 文案不一致、过渡动画缺失、小样式问题、安全审计Low漏洞 | 否 |

**逐项修复**（在Claude Code中输入）：

```
帮我修一下下面这些验收问题（按严重度从高到低排）：
[粘贴问题列表]

每个问题：定位源码文件 -> 改代码 -> 跑相关测试确认修好了 -> 重新验证那个页面
```

**修复原则**：
- 修复一个、验证一个、提交一个——不要攒批
- 每个修复 commit message 格式：`fix(scope): [验收修复] 问题描述`
- 严重和高级别问题必须在进入文档59之前全部修复

**修复完毕后最终确认**：

- [ ] 所有 `/qa-only` 失败页面重新运行并通过
- [ ] `/cso` 安全审计中所有严重/高危漏洞已修复，中危漏洞已处理
- [ ] `run_evals --tier all --compare baseline.json` 最终结果无5%以上劣化
- [ ] 三条用户旅程全部走通，无阻断

**验收签字**（在Claude Code中输入）：

```
帮我生成验收签字清单 acceptance-signoff.md，包含：

1. 验收执行摘要：
   - 验收日期、验收人
   - 总检查项数 / 通过数 / 不通过数
   - 已知遗留问题（含风险评估）

2. 分类通过率：
   - 页面功能：X/Y（百分比）
   - 安全审计：整体评分 + 各级漏洞数量
   - API 端点：X/Y（百分比，含正常/401/422/404分项）
   - Evals 对比：L1/L2/L3 各层通过率及与 baseline 对比
   - 用户旅程：3/3 通过

3. 发布建议（三选一）：
   - 可以发布（所有严重/高问题已解决）
   - 有条件发布（有遗留中/低问题，已评估风险可接受）
   - 不能发布（存在未解决的严重/高问题）
```

**如果出错**：

| 错误 | 原因 | 解决 |
|------|------|------|
| 修复 A 导致 B 回归（修复一个 bug 后其他页面的 `/qa-only` 通过率下降） | 修改的代码被多个页面共享（如公共组件、API 工具函数） | 修复前运行全量 `/qa-only` 记录基线通过率；修复后重新运行全量 `/qa-only` 对比；若出现回归，检查修改的文件是否被多个路由/组件引用 |
| 某个严重问题长时间无法修复 | 根因涉及底层架构（如数据库迁移冲突、认证流程改造） | 评估是否可以降级处理（如临时禁用该功能并记录为"已知问题"）；若为阻断性严重问题（如页面白屏），则暂停验收、回到对应阶段文档重新开发 |
| `git revert` 后 Evals 仍未恢复（劣化仍然 > 5%） | revert 了错误的 commit，或劣化由多个 commit 累积造成 | `git log --oneline --all --graph` 可视化分支历史；逐个 revert 怀疑的 commit 并每次运行 `run_evals` 验证；必要时 `git bisect` 二分定位 |
| 验收签字清单中"发布建议"为"不能发布" | 存在未解决的严重或高级别问题 | 回到修复循环，逐项处理严重/高问题；全部清零后重新生成验收签字清单；确认三个条件全部满足：严重=0、高=0、安全审计无Critical/High漏洞、Evals 劣化 <= 5% |
