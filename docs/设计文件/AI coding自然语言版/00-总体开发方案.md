## 一、工具链

### 1.1 九层工具

```
思考层： /office-hours  /plan-ceo-review  /plan-eng-review    ← Gstack
对齐层： /grill-with-docs → 产出 CONTEXT.md + ADR             ← Matt Skills
规格层： /opsx:propose  →  /opsx:apply  →  /opsx:archive      ← OpenSpec
实现层： 写测试(RED)  →  Claude生成(GREEN)  →  重构           ← TDD
质量层： L1单元  →  L2集成  →  L3 Golden  →  基线对比        ← Evals

门禁层： /no-mistakes（push 前全流水线） + git hooks + CI     ← no-mistakes
骨架层： branch  commit  tag  merge  revert  push              ← Git
原生层： Plan模式  Checkpoint  Hooks  Subagents               ← Claude Code

### 1.2 工具用途速查

| 工具 | 安装方式 | 在流程中的角色 |
|------|---------|--------------|

### 2.3 每个阶段的标准流程

```
                     ┌──────────────────────────────────────┐
                     │  1. git checkout -b phase-N/xxx       │
                     │  2. /opsx:propose "实现XXX功能"       │
                     │  3. /opsx:apply                       │
                     │       └── 内部TDD循环:                │
                     │           写测试 → Claude生成 → pytest │
                     │           git commit（每个模型/组件）  │
                     │       └── Evals检查:                  │
                     │           run_evals → 通过/tag 或     │
                     │           劣化 → /investigate → 修复   │
                     │  4. /code-review（双轴代码审查）               │
                     │  5. /qa <URL>（浏览器验收，如有UI）   │
                     │  6. git push no-mistakes（门禁→远程）│
                     │  7. git checkout main                 │
                     │     git merge --no-ff phase-N/xxx     │
                     │     git tag -a v0.N.0                 │
                     │  8. /opsx:archive                     │
```

**合并策略（重要）**：
- **日常阶段（43-58）**：本地 `merge --no-ff` + tag——单人开发不需要 PR，本地合并更轻快
- **发布阶段（59）**：`/ship` 走 **PR 仪式**（推送分支 → 开 PR → 人类审查 merge）——发布是重大事件，用 PR 留下审查痕迹
- **每个阶段收尾都要 `git push no-mistakes`**（把 feature 分支和 main 都推送到远程）——这是 CI（52 起生效）和门禁的前提；远程仓库在文档 42 Step 9 创建

**Evals 工具时序**：`run_evals` 在文档 43 Step 5.5 创建**轻量版 v1**（按 tier 标记运行全量 pytest），文档 52 升级为**完整版**（Golden 数据集分层 + 基线对比 + GitHub Actions CI）。43-51 期间 `--compare/--save-baseline` 参数不可用（报"完整版见文档52"），这是预期行为。

## 三、三层质量体系

### 3.1 TDD（实现正确性）

| 层级 | 内容 | 执行者 | 频率 |
|------|------|--------|------|
| 模型测试 | CRUD + 约束 + 默认值验证 | 用户写规格 → Claude生成pytest | 每个模型 |
| API测试 | 端点行为 + 认证 + 错误处理 | 同上 | 每个端点组 |
| 逻辑测试 | 状态机、融合算法、JWT签名 | 用户写（保留完整代码，A级） | 每个模块 |

### 3.2 Evals（质量稳定性）

| 层级 | 内容 | 通过标准 | 运行时机 |
|------|------|:------:|---------|
| L1 单元 | 纯函数逻辑（规则引擎、置信度、状态机） | ≥95% | pre-commit hook |
| L2 集成 | API端点行为（结构、状态码、认证） | ≥90% | 每个工具组完成 |
| L3 质量 | AI内容质量（科学性、诊断准确率、辅导安全性） | ≥70% | 每日收工、push前 |

### 3.3 劣化处理决策树

```
run_evals --compare baseline.json
  │
  ├── 无劣化 → git tag evals-ok-YYYYMMDD → 继续
  │
  ├── 劣化 ≤ 3% → 记录devlog → 继续（正常波动）
  │
  ├── 劣化 3-5% → /investigate → 定位golden样本 → fix commit → 重新run_evals
  │
  └── 劣化 > 5% → /investigate → 定位bad commit
        ├── 方案A: git revert <bad-commit> → run_evals确认恢复
        └── 方案B: 直接修复 → git commit -m "fix(golden-NNN): ..." → run_evals确认
```

## 四、Git骨架

Git 已嵌入每份文档的每个代码产出 Step 末尾，通过 Claude Code 执行。不存在独立的 Git 参考文档。以下是在所有文档中统一的规范。

### 4.1 操作格式

每个 Step 末尾的 Git 操作使用 Claude Code 对话格式：

```
**提交**（在Claude Code中输入）：

每次完成一个代码产出后，在 Claude Code 里这样提交：

"帮我把刚才的改动提交一下。先看一眼 git status 确认改了哪些文件，把同一个逻辑变更的文件挑出来，用 Conventional Commits 格式写 commit message。格式是 {type}({scope}): {description}，比如新增了一个模型和对应的测试，就写 feat(model): add School with pytest tests。"
```

### 4.2 Conventional Commits

```
<type>(<scope>): <subject>

类型: feat / fix / test / refactor / docs / chore / perf
范围: model / auth / review / exam / diagnosis / ocr / agent / eval / persona / guard / ui / golden-NNN
```

### 4.3 质量门禁

门禁在流程中的位置（43-51 期间 run_evals 为轻量版 v1，只跑 pytest 不做基线对比；52 升级后才有基线门禁）：

```
pre-commit  →  pytest tests/ --tb=short -x  (L1单元，<5秒)
commit-msg  →  验证 Conventional Commits 格式
pre-push    →  no-mistakes 流水线（review → test → docs → lint → push → PR → CI）
               （52 建成 Evals 后：run_evals --tier all --compare baseline.json，劣化>5%阻断）
```

**落地方式**：以上门禁**不要求手写配置**——在 Claude Code 中直接对话指挥即可：
- pre-commit / commit-msg：让 Claude Code 帮你配置 git hooks（文档 43 首阶段配置一次）
- pre-push：文档 42 已安装 no-mistakes（`git push no-mistakes` 自动触发全流水线）
- CI：文档 52 提供 `.github/workflows/evals-ci.yml`（L1 阻断 + L2/L3 劣化告警）

### 4.4 版本节奏

```

## 六、关键设计决策

### 6.1 什么时候用思考层，什么时候跳过

| 情况 | 做法 |
|------|------|
| Part 4 设计文档已明确定义功能 | 跳过 office-hours/ceo-review，直接 propose |
| 架构选型存在不确定性 | 用 eng-review |
| 产品方向/优先级有分歧 | 用 office-hours/ceo-review |

ChemAI项目中，Part 4 已经完成了详细的产品设计——所以大部分阶段跳过思考层，只保留少数架构重、边界模糊的阶段用 eng-review：数据模型（43，17个模型+RBAC）、诊断引擎（46，规则+置信度融合）、Agent架构（53，Gateway+ReAct+记忆数据流）。

### 6.2 Evals的粒度

不是"每生成一个模块就跑全量"——按工具组或每日收工。单个工具开发时只跑该工具的 pytest（秒级完成）。全量Evals在三个时机：工具组完成、每日收工、push前。

### 6.3 并行 vs 串行

| 可并行 | 必须串行 |
|--------|---------|
| 54/55/56（Agent工具组，都只依赖53） | 53必须最先（Agent框架） |
| 47/48/49（业务功能之间独立） | 44-46之间（出题→题库→诊断有数据依赖） |
| 50/51（学生端+家长端独立） | 58→59（验收通过才能发布） |

### 6.4 真实vibe coding vs 教程流程

教程是线性叙述的——每步都有预期结果。真实vibe coding是messy的：

- 一个prompt通常不是一次成功的，2-3轮修正是常态
- Evals劣化会打断开发节奏，需要切到修复模式
- 并行分支可能产生合并冲突

本文档的流程是**理想路径**。每份具体文档的Step中会标注"真实情况可能是..."，记录该步骤实际的试错次数和常见弯路。

### 6.5 项目记忆与决策记录（CLAUDE.md 演进 + ADR）

**CLAUDE.md 演进**：CLAUDE.md 不是写一次就完的——每个阶段收尾时，把本阶段沉淀的新约定（命名规范、模式惯例、踩坑教训）追加进去，让后续阶段和 AI 自动继承。每份文档的"完成标准"里已内置沉淀提醒，直接照做即可。

**ADR（架构决策记录）**：出现架构级决策时（用了 `/plan-eng-review`、`/grill-with-docs`，或实现中做出重大取舍），必须产出 ADR 文件：

```
docs/adr/YYYY-MM-DD-<短横线主题>.md
├── 背景    为什么需要这个决策
├── 决策    我们选择了什么（一句话）
├── 理由    为什么选它（对比至少一个替代方案）
└── 结果    预期影响与风险
```

在 Claude Code 中输入：`帮我为[决策主题]写一份 ADR，保存到 docs/adr/ 下`。

**决策不记录 = 没发生**——ADR 是下一轮 `/opsx:propose` 时 AI 对齐上下文的关键输入，也是复盘（文档 59 `/retro`）的事实来源。
