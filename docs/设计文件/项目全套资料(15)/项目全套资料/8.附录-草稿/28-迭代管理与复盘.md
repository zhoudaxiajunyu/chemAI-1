# 迭代管理与复盘 — ChemAI

> ChemAI 采用 2-4 周的迭代周期 + 评测驱动的完成标准。本文档记录迭代管理方法论、真实迭代记录和复盘方法论——不只是"总结做了什么"，而是"如果重新来过会怎么做"。

---

## 一、迭代周期模型

### 1.1 周期选择

ChemAI 根据功能复杂度采用弹性迭代周期：

| 功能类型 | 单人日 | 周期 | 示例 |
|---------|:----:|------|------|
| 简单功能 | < 2 | 1 周 | 加一个 tutoring tool（工厂模式下 15 行配置 + 评测） |
| 中等功能 | 3-10 | 2 周 | 学生端练习页与教师端考试对接（前后端 + 数据管道） |
| 复杂功能 | 10+ | 4 周 | 答题卡 OCR 批改系统（OCR 接入 + 识别纠错 + 批改管线 + 诊断生成） |
| 架构变更 | 5-15 | 2 周（高密集） | v1→v2 Agent 架构升级（不改功能，改底层） |

**为什么不是固定的 2 周 Sprint？**
- AI 产品的不确定性高于传统软件。2 周的固定节奏适合"知道要做什么"的维护期，不适合"探索该怎么做"的 0→1 期
- 4 周的周期给复杂功能（如 OCR 管线）足够的"探索 + 实现 + 评测"时间，不会因为 Sprint 边界产生半成品

### 1.2 一个迭代的完整结构

```
第 1 天：迭代计划（2 小时）
  输入：
    - 上一迭代评测报告（哪个维度下降了？哪个回归触发了？）
    - 教师反馈汇总（微信群 + 培训交流）
    - Product backlog 优先级
  输出：
    - 本次迭代功能清单（≤ 5 项核心功能，防止 scope creep）
    - 每个功能的评测场景定义（PM 写业务场景，工程师写断言）
    - "完成标准"：不是"代码写完了"，而是"对应评测场景 100% 通过"

第 1-N 天：功能开发 + 评测编写
  流程：
    工程师先写评测（确认评测失败——功能还没做）
    → 写实现代码（确认评测通过）
    → PM 检查评测场景是否覆盖真实用户场景
  每个功能至少 3 个评测场景：
    - 正常路径（Happy path）
    - 边界路径（Edge case）
    - 错误路径（Error handling）

每天：10 分钟站会
  三个问题：
    1. 昨天做了什么？（必须关联到评测场景编号）
    2. 今天做什么？（预估是否有阻塞风险）
    3. 有没有需要 PM 决策的问题？
  规则：
    - 禁止在站会上讨论技术细节（技术讨论会后另外安排）
    - 如果连续 2 天没有进展，PM 主动约 1:1 排查阻塞

最后一天：迭代复盘（1.5-2 小时）
  三件事（详见第四节）：
    1. 评测数据 review
    2. 做对了什么（值得继续的做法）
    3. 做错了什么 / 下次怎么做
```

### 1.3 完成标准

ChemAI 的"完成"不是"代码合并到 main 分支"，而是：

```
✅ 功能对应的评测场景 100% 通过（确定性 + API）
✅ 已有评测无退化（回归层 + 安全层 100%）
✅ 新评测已加入 CI 套件
✅ 前端对教师/学生可用（种子老师可以在下一次考试中使用）
✅ 如果涉及数据库变更 → 迁移脚本已测试
✅ 如果涉及 Prompt 变更 → 评测路由准确率不低于变更前
```

## 二、需求管理与优先级

### 2.1 需求来源

```
教师反馈（最高权重）
  ├─ 微信群日常反馈
  ├─ 培训交流中的需求
  ├─ 诊断报告修正记录（教师修正了 AI 的判断 → 说明这个场景 AI 做不好）
  └─ 使用数据（活跃率下降 → 可能卡在某个流程）

评测报告（客观信号）
  ├─ 评测维度下降 > 5% → P1 修复
  ├─ 评测维度下降 > 10% → P0 修复（阻断 CI）
  └─ null 维度 → 评测体系的 roadmap

技术债务
  ├─ 已知架构差距（来自 CLAUDE.md known_gaps）
  ├─ 代码中的 TODO/FIXME
  └─ 性能瓶颈（P95 延迟上升趋势）

战略方向
  ├─ 产品路线图中的下个里程碑
  └─ 学校采购周期（学期初和学期末的功能重点不同）
```

### 2.2 优先级框架

ChemAI 使用"影响 × 信心 × 投入"三维评估：

| 维度 | 评分标准 |
|------|---------|
| **影响** (1-5) | 这个功能解决了多少教师的痛点？1="nice to have"，5="没有这个活不下去" |
| **信心** (1-5) | 我们多确定这个方案是对的？1="纯猜测"，5="有种子教师反馈和评测数据支撑" |
| **投入** (S/M/L/XL) | 需要多少单人日？S < 2, M 3-10, L 10-20, XL > 20 |

优先级 = 影响 × 信心 / 投入。高影响 + 高信心 + 小投入 = 立马做；高影响 + 低信心 = 先做原型验证。

**当前（2026.Q3）优先级排序**：
1. 种子校体验优化（教师反馈中提到的问题）— 影响 5, 信心 4, 投入 M
2. 评测场景补全（null 维度 → 有覆盖）— 影响 4, 信心 5, 投入 M
3. 家长端完善（推送 + 互动）— 影响 3, 信心 3, 投入 L
4. 多校管理面板 — 影响 2, 信心 3, 投入 XL → **暂缓**

## 三、真实迭代记录

### 迭代 1：学生端数据打通（2026-07-03）

**起点**：学生端练习页和错题页完全空白。教师发布的考试学生端不可见。学生端和教师端是两个独立的信息孤岛。

**做了什么**：
- 合并 EXAM 和 PRACTICE 查询（SQL 层面统一教师发布的考试和学生自主练习）
- 创建 student persona（YAML 配置 + TOOL_META 关联）
- 修复前端 API 解析逻辑（`d.success` 重复判断 → 抽象为 `ensureData()` helper）
- 学生端对话页面接入 v2 Agent（SSE 流式）

**评测变化**：
- 确定性评测：新增路由层评测 7 个（persona 隔离方向）
- API 评测：student persona 路由准确率初始 78%（后续迭代通过输入引导提升到 87%）

**做对了什么**：
- 在合并 EXAM/PRACTICE 查询前先写了评测场景（"学生端应看到教师发布的考试"），避免了数据合并出错
- 学生端 Persona 隔离评测在开发第一天就通过——"学生看不到教师工具"从一开始就是正确的

**教训**：
- `d.success` 这种重复模式（在 4 个页面各写了一遍）应该在第一遍出现时就抽象成 helper，而不是等第四遍
- 前端和 Agent 的联调花的时间比预期多 50%——SSE 事件在前端的消费逻辑应该先 mock 好

### 迭代 2：多轮对话修复 + OCR 管线完善（2026-07-04 上午）

**起点**：学生端多轮对话断裂——发"我不知道"后 Agent 重新自我介绍。这是阻碍学生正常使用的 P0 问题。

**做了什么**：
- 从 InMemorySaver 切换到 AsyncSqliteSaver（ADR-002）
- `cid`（conversation_id）存入前端 sessionStorage，跨页面保持
- SSE dedup 扩展：从仅去重工具层（CCE dedup）扩展到文本层（防止 LLM 重复输出工具结果）
- OCR 管线添加 teacher_id 过滤（安全评测发现的权限隔离漏洞）
- `GuardState._route` 在传给 LLM 前剥离（防止 LLM 在回复中输出路由信息）

**评测变化**：
- 确定性评测：新增 27 个场景（边界层 12 + 安全层 6 + 回归层 5 + 其他 4）
- 安全层（Persona 隔离 + OCR 权限）：100% 通过

**做对了什么**：
- 先把多轮对话断裂复现为评测场景（"同一 cid 下，第二条消息应能看到第一条消息的上下文"），再修复
- 端口僵尸问题虽然花了 2 小时排查，但直接促成了 ADR-008（Docker 单容器部署）——短期内痛苦，长期正确

**教训**：
- 端口僵尸进程问题花了 2 小时排查。应该在上一个迭代结束时就 `docker compose down` 清理环境。**每次迭代结束时清理开发环境应成为标准操作。**
- AsyncSqliteSaver 的文件路径如果没有显式指定，默认在 `./checkpoints.db`——和我们的 `chemai_checkpoints.db` 不同。花了 20 分钟才发现是路径问题。

### 迭代 3：工具集升级 + tutoring 工厂模式（2026-07-04 下午）

**起点**：只有 `balance_equation` 和 `chemistry_tutor` 两个化工工具，缺少离子方程式、物质的量、氧化还原、化学平衡、元素周期律、有机推断等核心考点的专属辅导工具。

**做了什么**：
- 用工厂模式（ADR-007）创建 7 个 tutoring tool：`ionic_equation_tutor`、`stoichiometry_tutor`、`redox_tutor`、`equilibrium_tutor`、`periodic_law_tutor`、`organic_tutor`，复用已有的 `chemistry_tutor`
- 实现 TOOL_META 自动注册（ADR-011）——每个工具声明 personas 和 call_limit
- 更新所有 Persona YAML 的 available_skills（student 新增 6 个 tutoring tool）
- 评测 `test_yaml_skills_all_in_auto` 自动验证 Persona YAML 与 TOOL_META 一致性
- Context Trim 混合策略实现（ADR-010）——滑动窗口 + 关键字 + LLM 摘要

**评测变化**：
- 确定性评测：新增 18 个（回归层全套 + 工具一致性评测）
- API 评测：新增 15 个（tutoring tool 路由场景 + 工作流场景）
- 新增评测类型：`test_tutor_factory` parametrized 覆盖所有 tutoring tool

**做对了什么**：
- 工厂模式是本次最优决策——后续新增 `periodic_law_tutor` 和 `organic_tutor` 各只用了 10 分钟（15 行配置 + 加两个 YAML skill）。如果仍然逐个手写，每个 60 行 + 评测 + bug fix，至少半天一个。
- `test_yaml_skills_all_in_auto` 评测在开发过程中发现了 2 次 YAML 和 TOOL_META 的不一致——都是在"加工具改 TOOL_META 但忘了更新 YAML"的时候。**评测在 5 秒内捕获了人肉容易漏的配置错误。**

**教训**：
- Context Trim 的 LLM 摘要 prompt 第一版太泛——"请总结以上对话"导致化学方程式被错误简化（`2Na + 2H2O → 2NaOH + H2↑` 被总结为"钠和水的反应"）。第二版明确要求"保留所有化学式和系数"。
- 7 个 tutoring tool 的评测数据一开始写在一个文件里 → 文件太长（400+ 行）。应该一开始就用 parametrize 分离数据和逻辑。

### 迭代 4：种子校部署 + 演示数据准备（2026-07-05）

**起点**：产品在开发环境能跑，但种子学校需要在自己的服务器上部署。

**做了什么**：
- Docker Compose 配置完善（healthcheck、volume 挂载、环境变量模板）
- 邵阳县第一中学演示数据导入（3 名教师、66 名学生、13 次考试、324 道题、9600 条答题记录）
- `.env.example` 完善（所有环境变量带注释和默认值）
- 部署文档 + 教师培训录屏

**评测变化**：确定性评测 86 个全部通过，API 评测路由准确率 87%。

**做对了什么**：演示数据使用的是真实学校数据（脱敏），不是虚构数据——种子老师在 demo 中看到的数据模式就是他们将来会看到的。

**教训**：演示数据的导入脚本花的时间比预期多——不同来源的数据格式不一致。下次应该在数据收集阶段就统一格式。

## 四、复盘方法论

### 4.1 复盘 vs 日报

很多人以为复盘就是"总结一下这周做了什么"。那不是复盘，那是日报。

**真正的复盘回答一个问题：如果下周重新做这个迭代，我会怎么做？**

| | 日报/周报 | 复盘 |
|---|---------|------|
| **回答的问题** | "做了什么" | "如果重新来会怎么做" |
| **视角** | 事后描述 | 面向未来的改进 |
| **产出** | 清单 | 可执行的改进措施 |
| **价值** | 信息同步 | 能力提升 |

### 4.2 ChemAI 复盘三问

每次迭代结束复盘，全组一起 1.5-2 小时，聊三件事：

**第一问：评测数据（30 分钟）**

```
- 本次迭代新增评测数：X
- 本次迭代评测通过率变化：Y% → Z%
- 有没有评测退化的维度？
  - 是功能问题（代码改坏了）？
  - 是评测写太严了（场景不合理）？
  - 是模型悄悄变了（API 评测波动）？
  - null 维度的数量有没有减少？
- KPI 仪表盘各项指标的当前状态
```

**第二问：做对了什么？（30 分钟）**

不是"这周完成了什么功能"，而是"哪些做法值得下次继续"。

示例：
- ✅ "评测先行的模式很好——功能开发前先把场景定清楚，少了很多返工。下次继续。"
- ✅ "工厂模式让加 tutoring tool 从半天变 10 分钟。以后遇到 > 3 个类似功能的场景，先花 1 小时做抽象。"
- ✅ "每天站会控制在 10 分钟，效率高。技术讨论会后再约，不浪费其他人的时间。"

**第三问：做错了什么 / 下次怎么做？（40 分钟）**

不是批斗会，是改进会。每个"做错了"必须带一个"下次怎么做"。

示例：
- ❌ "功能 A 和功能 B 在同一个工具文件里改，产生合并冲突。" → ✅ "下次拆分成独立 tool 文件。工具文件遵循单一职责——一个文件一个工具。"
- ❌ "端口僵尸问题排查了 2 小时。" → ✅ "每次迭代结束执行 `docker compose down`，纳入迭代 checklist。"
- ❌ "Context Trim 的摘要 prompt 第一版丢失了化学式。" → ✅ "涉及化学内容的 prompt 必须在评测中验证'化学式保留'这个维度。"

### 4.3 复盘产出转化机制

复盘最危险的结果是"聊完了，散会了，下次继续犯同样的错误"。

ChemAI 的转化机制：

```
复盘结论 → 转化为以下之一：
  ├─ 评测场景（"这个 bug 下次不能复现" → 加回归评测）
  ├─ ADR（"这个架构决策应该被记录" → 写 ADR）
  ├─ 开发规范（"以后加 tool 要同时更新 TOOL_META 和 YAML" → 写入 CLAUDE.md）
  ├─ Checklist（"迭代结束清理环境" → 加入迭代计划 checklist）
  └─ Backlog item（"这个技术债需要单独一个迭代来修" → 进 backlog）
```

### 4.4 复盘产出的真实案例

历次复盘的结论都转化为了具体行动：

| 复盘发现 | 转化 | 效果 |
|---------|------|------|
| "端口冲突浪费大量时间" | ADR-008：Docker 单容器部署 | 彻底解决 |
| "每次加 tool 要改 4 个地方" | ADR-011：TOOL_META 自动注册 | 改 4 处 → 改 2 处，评测自动验证 |
| "SSE dedup 只覆盖了工具层" | 扩展到文本层 dedup | 学生不再看到重复回复 |
| "评测跑太慢了（API 评测混在 CI 里）" | 确定性评测和 API 评测分离 | CI 只跑确定性（5s），API 评测单独触发 |
| "前端 d.success 重复模式" | 抽象为 ensureData() helper | 4 处 → 1 处 |
| "Context Trim 丢失化学式" | 摘要 prompt 强化"保留化学式和系数" | 评测验证通过 |
| "演示数据导入格式不一致" | 建立数据导入规范文档 | 后续导入不再出格式问题 |

### 4.5 复盘有效性检验

一个迭代结束后的复盘如果没有产出"下次会怎么做"的结论，这个复盘就是无效的。

如果连续三个迭代的复盘都在重复同一个"做错了什么"——说明复盘结论没有转化，或者转化了但没执行。PM 需要介入排查流程问题。
