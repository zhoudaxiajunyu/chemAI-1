# 原型验证与POC — ChemAI

> AI 产品最大的风险不是"做不出来"，而是"做出来了但没人用"或"根本做不出来"。原型验证和 POC 的目的是在投入大量工程资源之前，用最低成本回答两个问题：**方向对不对**和**技术能不能做**。

---

## 一、AI 原型的特殊性

### 1.1 为什么 AI 原型不能照搬传统软件的做法

传统软件做原型：画交互稿 → 做可点击 Demo → 给用户试用 → 收集反馈。这个过程验证的是"用户能不能理解这个界面"。

AI 产品做原型需要多验证一层：**模型能不能做这件事**。一个再精美的界面，如果背后的 AI 配平化学方程式只有 60% 的准确率，产品就没有任何价值。

| 传统软件原型 | AI 产品原型 |
|------------|-----------|
| 验证交互逻辑 | 验证交互逻辑 **+ 模型能力边界** |
| 用 Figma/Axure 画图 | 用 AI 生成工具出可交互 HTML |
| 人工走查 | 自动化评测 + 人工审核 |
| 原型 = 高保真 UI | 原型 = UI + 最小可用模型链路 |
| 原型过了就进入开发 | 原型过了 → POC 验证技术可行性 → 才进入开发 |

### 1.2 ChemAI 的实际做法

ChemAI 遵循"先验证模型能力，再验证产品价值"的两阶段验证：

```
Session 02: 模型能力验证
  "DeepSeek 能不能正确配平化学方程式？"
  → 3 个方程式、1 天时间、80% 准确率
  → 结论：方向可行，但需要四维审核引擎兜底

Session 07-08: 产品原型验证
  "教师愿不愿意用 AI 出题+批改？"
  → HTML 原型 + 3 位教师试用
  → 结论：3/3 表示会继续用，进入 POC
```

## 二、AI 原型生成工作流

### 2.1 六步法

基于 Google I/O 2025 发布的 Stitch 工具链、v0/Bolt/Lovable 等工具的实践，以及 ChemAI 的实际经验，AI 原型应遵循以下流程：

```
Step 1: 结构化 PRD 输入
  不是把整个 PRD 丢给 AI，而是抽取原型需要的部分：
  - 目标用户（一句话）
  - 核心场景（1-3 个）
  - 功能边界（做什么、不做什么）
  - 设计约束（风格、设备、技术栈）

Step 2: AI 生成多方案原型方案
  使用 Google Stitch / v0 / Bolt 生成 3-5 个方向：
  - 信息架构方案（页面结构、导航逻辑）
  - 视觉风格方案（色彩、排版、组件风格）
  - 关键交互方案（核心流程的交互细节）

Step 3: 方案评审与筛选
  对照原始需求检查：
  - 信息架构是否完整？（有没有遗漏流程步骤？）
  - 是否符合用户心智模型？（教师看到"考试工作台"能理解吗？）
  - 技术可实现性？（AI 生成的 UI 能否直接对接后端 API？）

Step 4: AI 出可交互原型
  选定方向后，用 AI 工具生成可交互 HTML/CSS：
  - Google Stitch：适合设计驱动，输出 Figma + HTML
  - v0 (Vercel)：适合 React/Tailwind 组件，工程师可直接使用
  - Bolt.new：适合全栈原型（前端+后端+数据库）
  - Lovable：适合非技术人员快速出 MVP
  ChemAI 选择：直接生成 HTML/CSS（Vanilla JS），跳过框架层

Step 5: 调整与优化
  对 AI 生成的原型进行人工精调：
  - 修复 AI 理解偏差（如"考试工作台"被理解为"题库浏览器"）
  - 补充领域细节（化学公式渲染、配平步骤展示）
  - 对齐设计系统（颜色、间距、字体统一）

Step 6: 输出可交互原型
  最终产物：
  - 一组可交互 HTML 页面（教师端 5 页 + 学生端 4 页）
  - 一份设计决策记录（为什么选这个方案、放弃了哪些方向）
  - 一份用户反馈记录（种子教师试用的观察和访谈）
```

### 2.2 ChemAI 实际案例

**教师端考试工作台原型过程**：

1. **PRD 输入**："教师需要在考试工作台中完成'选择知识点→设置难度→AI生成题目→审核题目→发布给班级'的完整流程。不是题库浏览器，是考试制作工具。"
2. **Stitch 生成 3 个方向**：① 纵向步骤条（类似问卷制作）② 横向标签页（类似 Excel 多 sheet）③ 侧边栏+主区域（类似邮件客户端）
3. **教师反馈**：纵向步骤条最符合"一步一步来"的心智模型，但需要在每步可以回退修改
4. **最终原型**：纵向 4 步骤（知识点→难度→生成→审核→发布）+ 每步可回退 + 已生成的题目可单独编辑/删除/重新生成

## 三、POC 验证

### 3.1 POC 的核心原则

POC（Proof of Concept）和原型的区别：

| 原型 | POC |
|------|-----|
| 验证"用户能不能理解" | 验证"技术上能不能做到" |
| 交互层面 | 模型+系统层面 |
| 可以 mock 数据 | 必须接通真实 AI 链路 |
| 可以跳过边界情况 | 必须验证核心假设的极限 |
| 产出：可交互 Demo | 产出：Go/No-Go 决策 |

POC 的核心原则：**用 5-15% 的完整实现成本，拿到 kill or continue 的信号。** 如果 POC 证明方向不对，损失 1-2 周而不是 2-3 个月。

### 3.2 POC 六步法

参照 AWS GLOE 框架和 Microsoft POC→MVP 方法，结合 ChemAI 实践：

```
Step 1: 定义核心假设
  把产品风险转化为可验证的假设：
  ✗ "AI 能帮助化学老师"（太模糊，无法验证）
  ✓ "AI 配平化学方程式的准确率 > 90%，且教师信任度 > 80%"

Step 2: 搭建最小技术验证
  只搭建验证假设所需的最小链路，不管其他：
  - ChemAI POC 只需要：一个对话界面 + balance_equation 工具 + DeepSeek API
  - 不需要：登录系统、数据库、多角色、前端美化
  - 原则：能少写一行代码就少写一行

Step 3: 跑通关键链路
  用 3-5 个代表性场景跑通端到端：
  - 用户输入 → LLM 理解 → 工具调用 → 结果返回 → 用户看到
  - 每个场景只验证一个假设

Step 4: 量化评估
  用数据说话，不做主观判断：
  - 配平准确率：X/Y 个方程式（用教研顾问标注的 ground truth）
  - 用户满意度：N/N 位种子教师表示"会继续用"
  - 关键失败模式：哪些类型的方程式配平会出错？

Step 5: Go/No-Go 决策
  ┌─────────────────────────────────────┐
  │ Go 标准（ChemAI 实际通过标准）：       │
  │ ✅ 配平准确率 > 80%（可接受，后续用    │
  │    四维审核引擎兜底到 100%）           │
  │ ✅ 3/3 教师表示"会继续用"              │
  │ ✅ 未发现不可逾越的技术障碍             │
  │                                      │
  │ No-Go 标准（如果出现则终止项目）：      │
  │ ❌ 配平准确率 < 60%（不可接受）         │
  │ ❌ 2/3 以上教师表示"不会用"            │
  │ ❌ 核心技术路径被证明不可行             │
  └─────────────────────────────────────┘

Step 6: 如果 No-Go
  不是失败——是用 1 周避免了 3 个月的错误方向。
  - 记录：为什么不可行？哪些假设被推翻了？
  - Pivot：能否调整方向？还是彻底终止？
```

### 3.3 ChemAI 实际 POC 案例

**案例 1：AI 配平能力验证（Session 02）**

| 维度 | 详情 |
|------|------|
| **核心假设** | DeepSeek 能否正确配平高中化学方程式？ |
| **最小验证** | 3 个方程式：`Fe + O2 → Fe2O3`（基础难度）、`Cu + HNO3(稀) → Cu(NO3)2 + NO + H2O`（中等等难度）、`KMnO4 + HCl → KCl + MnCl2 + Cl2 + H2O`（高等难度） |
| **结果** | 基础 100%、中等 80%、高等 60% |
| **决策** | Go——LLM 配平有基础能力但不可靠，需要四维审核引擎兜底（系数平衡算法 + RDKit 分子结构验证作为确定性保障） |

**案例 2：OCR 答题卡识别验证（Session 11）**

| 维度 | 详情 |
|------|------|
| **核心假设** | OCR 能否从手写答题卡中正确识别化学符号（可逆号、三角号、上下标）？ |
| **最小验证** | 10 张真实学生答题卡，对比三家 OCR（百度 OCR / MinerU / 自研简单方案） |
| **结果** | 百度 OCR：化学符号识别率 ~60%，MinerU：~85%，自研：~50% |
| **决策** | Go——选择 MinerU 为主 + 百度 OCR 为 fallback 的双路架构 |

**案例 3：Agent 路由架构验证（Session 13）**

| 维度 | 详情 |
|------|------|
| **核心假设** | Agent 能否正确判断用户意图并选择对应工具？ |
| **最小验证** | 15 个意图分类场景（"帮我配平"→balance_equation，"什么是氧化还原"→chemistry_tutor，"搜 2023 年高考真题"→search_exam_bank） |
| **结果** | v0 (pydantic-ai) 路由准确率 ~70%，v1 (多Agent) ~75%，v2 (单 Agent) 87% |
| **决策** | Go——多次架构迭代直到达到可接受的准确率 |

## 四、原型验证与 POC 的衔接

原型和 POC 不是串行的两个阶段，而是两根并行轨道：

```
       原型轨道                    POC 轨道
     （验证交互）               （验证技术）
         │                          │
Week 1: 生成 UI 原型 ──────── 验证 LLM 基础能力
         │                          │
Week 2: 教师试用反馈 ──────── 验证端到端链路
         │                          │
Week 3: 迭代原型      ──────── 量化评估 + Go/No-Go
         │                          │
         └──────────┬───────────────┘
                    ▼
              双轨合并：进入工程实现
```

**关键原则**：原型验证的是"人能不能用"，POC 验证的是"AI 能不能做"。**两者都要在写正式产品代码之前完成。**

## 五、常见错误

| 错误 | 后果 | ChemAI 的做法 |
|------|------|-------------|
| 跳过 POC 直接开工 | 开发了 2 个月发现模型做不了 | Session 02 先用 1 天验证配平能力 |
| 原型做太完美 | 浪费 3 周做了个"看起来真"但核心链路没验证的原型 | HTML 原型，不写后端，不接数据库 |
| POC 只测 happy path | 上线才发现边界情况全部崩溃 | 每个假设至少测 1 个 happy path + 1 个 edge case |
| Go/No-Go 没有量化标准 | "感觉还行"→ 后续反复纠结 | 明确的量化门槛（配平 > 80%、教师 ≥ 2/3） |
| 把 POC 代码当产品代码用 | POC 的快捷写法变成生产环境的定时炸弹 | POC 代码标注 `# POC ONLY`，进入工程实现阶段全部重写 |
