# 技术选型与工具链 — ChemAI

> POC 验证了 AI 能做这件事。接下来的问题是：用什么做？技术选型决定了产品的能力边界、开发速度和长期维护成本。每个选择都对应着被放弃的替代方案和需要承担的后果。

---

## 一、选型方法论

### 1.1 选型框架

ChemAI 的技术选型遵循三条原则：

1. **够用就好，不为未来过度设计**：选当前阶段需要的最简单方案，保留向上升级的路径
2. **优先选有社区验证的方案，避免"自研陷阱"**：自研只在现有方案确实满足不了需求时才考虑
3. **每个选择记录为 ADR（架构决策记录）**：不只记录"选了什么"，更记录"为什么选"和"放弃了什么"

选型的四个维度：

```
        成本
         ↑
         │  象限 II          │  象限 I
         │  高成本/低匹配     │  高成本/高匹配
         │  (避免)           │  (规模化时考虑)
         │                   │
         │  ─────────────────────────→ 匹配度
         │                   │
         │  象限 III         │  象限 IV
         │  低成本/低匹配     │  低成本/高匹配
         │  (不选)           │  ★ 目标区域
         │                   │
```

### 1.2 选型流程

ChemAI 的技术选型遵循五步流程，每步都有对应的 ADR：

```
Step 1: 列出候选方案（不做预判，先穷举）
  Step 2: 定义评估维度（对当前阶段最重要的是什么？）
  Step 3: 对比评分（定量+定性，不做"感觉"）
  Step 4: 做决策 + 写 ADR（记录为什么不选其他方案）
  Step 5: 保留升级路径（如果将来需要换，成本多大？）
```

## 二、LLM Provider 选型

### 2.1 候选方案

| Provider | 模型 | 输入价格 | 输出价格 | 优势 | 劣势 |
|----------|------|---------|---------|------|------|
| DeepSeek | deepseek-chat | ¥1/百万 token | ¥2/百万 token | 性价比最优、中文理解好 | 偶发维护窗口（2-4h） |
| 小米 MiMo | moonshot-v1-8k | ¥0.8/百万 token | ¥0.8/百万 token | 成本最低 | API 仍处 beta 阶段 |
| 阿里通义千问 | qwen-turbo | ¥0.8/百万 token | ¥2/百万 token | 稳定、有化学领域能力 | 峰值时段偶发限流 |
| 智谱 GLM | glm-4-flash | ¥0.1/百万 token | ¥0.1/百万 token | 国产合规 | 化学领域能力弱于 DeepSeek |
| OpenAI | GPT-4o | ¥40+/百万 token | ¥80+/百万 token | 能力最强 | 成本高、数据出境风险、国内访问不稳定 |
| 自部署 Llama | Llama 3.1 70B | 硬件成本 | 硬件成本 | 数据不出境 | 硬件投入大、需要 ML 运维能力 |

### 2.2 决策

**选择：多 Provider 四级 fallback 路由，而非单 Provider。**

```
首选: MiMo (moonshot-v1-8k) — 成本最低
  ↓ 不可用
主力: DeepSeek (deepseek-chat) — 性价比最优
  ↓ 不可用
备选: 通义千问 (qwen-turbo) — 第一 fallback
  ↓ 不可用
兜底: 智谱 GLM (glm-4-flash) — 第二 fallback
```

**理由**：
- 国内 AI 厂商的 API 稳定性参差不齐——DeepSeek 偶尔维护、通义千问偶发限流、MiMo 在 beta 阶段。依赖单一 Provider = 服务可用性 ≤ 该 Provider 的可用性
- 四级 fallback 将可用性从 ~99%（单 Provider）提升到 > 99.5%
- 月度 LLM 成本 < ¥200（大部分请求走 MiMo 和 DeepSeek）
- 不选 OpenAI/Claude 的原因：成本高出 20-50 倍、数据出境合规风险、国内网络不稳定

**放弃的方案**：
- 单 Provider：可用性不够
- 自部署 Llama：硬件投入 ¥2-5 万 + ML 运维能力 = 种子期 ROI 不匹配
- OpenAI/Claude：成本 + 合规 + 网络三重问题

**升级路径**：随着用量增长，当 DeepSeek API 成本超过自部署硬件成本时，可切换到自部署 DeepSeek（DeepSeek 模型开源）。

## 三、Agent 框架选型

### 3.1 候选方案

| 框架 | 类型 | 优势 | 劣势 |
|------|------|------|------|
| **LangGraph** | 有状态图 Agent | checkpoint 持久化、SSE 流式、社区成熟 | 框架抽象层有一定复杂度 |
| **CrewAI** | 多 Agent 角色扮演 | 角色分工清晰 | 偏重 Agent 间对话，ChemAI 核心需求是工具调用准确率 |
| **AutoGen** | 多 Agent 协作 | 微软支持、人在回路 | 更适合对话式多 Agent，不是工具密集型场景 |
| **OpenAI Agents SDK** | 单 Provider Agent | 简单直接 | 绑定 OpenAI，国内不适用 |
| **Pydantic AI** | 类型安全 Agent | FastAPI 原生集成 | 生态较小，路由准确率不够（ChemAI 实测 ~70%） |
| **自研框架** | 完全掌控 | 灵活性最高 | 需要 2-3 个月投入，checkpoint/streaming/error recovery 都需要自己写 |

### 3.2 实际迭代过程（四轮）

ChemAI 的 Agent 框架选型不是"一次选对"，而是经历了**四次迭代验证**：

| 迭代 | 框架 | 路由准确率 | 问题 |
|:--:|------|:--:|------|
| v0 | Pydantic AI | ~70% | 路由不稳定，"离子方程式"常被错误分到"出题"而非"辅导" |
| v1 | LangGraph Multi-Agent（Coordinator + Router + 6 Sub-Agent） | ~75% | 架构复杂，Coordinator 路由仍不够准，延迟高（2 次 LLM round-trip） |
| v2 | LangGraph 单 Agent（`create_react_agent` + Persona 过滤） | **87%** | — |
| 保留 | LangGraph Multi-Agent（v1） | ~75% | 保留为 fallback，通过 API 参数 `version` 切换 |

### 3.3 决策

**选择：LangGraph `create_react_agent`（单 Agent）。**

**理由**：
- 让 LLM 自己从 25 个工具中选择，路由准确率 87%，高于 Coordinator+Router 模式的 75%
- 去掉 Coordinator 和 Router 两个 LLM 调用节点 → 延迟降低 40%（P50 从 ~3s 降到 ~1.5s）
- Checkpoint 持久化（AsyncSqliteSaver）开箱即用
- SSE 流式输出（`astream_events`）原生支持
- 社区成熟（LangChain 生态核心组件，文档和问题解答丰富）

**放弃的方案**：
- CrewAI/AutoGen：偏向 Agent 间对话协作，ChemAI 的核心需求是**工具调用准确率**，不是 Agent 之间对话
- OpenAI Agents SDK：绑定 OpenAI，国内不可用
- Pydantic AI：实测路由准确率不够
- 自研：种子期 2-3 个月投入自研框架，ROI 不匹配——LangGraph 已经解决了我们需要的问题

**升级路径**：当前单 Agent + Persona 过滤足够。如果未来需要真正的多 Agent 协作（如出题 Agent 和诊断 Agent 独立运行、异步协作），LangGraph 的 `StateGraph` API 支持从单 Agent 升级到多 Agent，迁移成本可控。

## 四、前端选型

### 4.1 候选方案

| 方案 | 优势 | 劣势 |
|------|------|------|
| **React + Next.js** | 组件化、生态最大、SSR | 学习成本、构建复杂度、bundle 体积 |
| **Vue 3 + Nuxt** | 中文社区好、上手快 | 与 React 类似的框架成本 |
| **Vanilla JS + Vite** | 零框架开销、简单直接 | 没有组件化、代码组织靠自律 |
| **HTMX + 服务端渲染** | 极简 | 不适合 Agent SSE 流式交互 |

### 4.2 决策

**选择：Vanilla JS + Vite + Tailwind CSS + KaTeX/mhchem。**

**理由**：
- 页面数量少：教师端 5 页 + 学生端 4 页 + 家长端 1 页 = 不到 10 个页面
- 团队 1 人全栈：没有多人协作的组件复用需求
- 没有复杂的客户端状态管理：状态主要在后端和数据库
- Vite 提供开箱即用的 HMR、build、proxy（`/api` → `localhost:8000`）
- 框架的构建复杂度 > 当前阶段的实际收益
- KaTeX + mhchem：唯一能正确渲染化学方程式的开源方案

**放弃的方案**：
- React/Vue：当前页面数量和团队规模下，框架引入的收益（组件化、状态管理）小于成本（构建配置、学习曲线、bundle 体积）
- HTMX：不适合 SSE 流式 Agent 对话场景

**升级路径**：当页面数量超过 20 个或团队扩大到 3+ 前端工程师时，可以渐进式引入 React（Vite 支持 React 插件，迁移成本可控）。

## 五、数据库选型

### 5.1 候选方案

| 方案 | 优势 | 劣势 |
|------|------|------|
| **SQLite + WAL** | 零运维、单文件、WAL 支持读写并发 | 写操作串行化、不适合高并发 |
| **PostgreSQL** | 功能完整、并发强、JSONB | 需要独立安装运维 |
| **MySQL** | 国内使用广泛 | 与 PostgreSQL 类似运维成本 |

### 5.2 决策

**选择：SQLite + WAL 模式。配置：**
```sql
PRAGMA journal_mode=WAL;        -- 写前日志，支持读写并发
PRAGMA synchronous=NORMAL;       -- 平衡安全与性能
PRAGMA foreign_keys=ON;          -- 外键约束
PRAGMA cache_size=-8000;         -- 8MB 缓存
PRAGMA busy_timeout=5000;        -- 5s 锁等待超时
```

**理由**：
- **零运维成本**：不需要单独安装、配置、备份数据库服务。`docker compose up` 一键全启动。
- **WAL 模式**：读者不阻塞写者，写者不阻塞读者——满足单校部署（< 50 在线）的并发需求。
- **Docker 单容器**：应用 + 数据库在一起，适合学校本地化部署。
- **SQLAlchemy ORM 抽象**：如果将来需要切换到 PostgreSQL，改一行连接字符串即可，SQL 方言差异通过 ORM 层吸收。

**放弃 PostgreSQL 的理由**（明确记录，不是"没想到"）：
一个部署给单个学校的本地化工具，不需要分布式数据库。运维 PostgreSQL 实例的成本（安装、配置、备份、升级、故障恢复、监控）远超 ChemAI 现阶段的实际需求。**等到有 50+ 所学校同时在线再迁移到 PostgreSQL，ROI 才对。**

**升级路径**：当并发达到瓶颈（同时在线 > 50 人或多校共享实例时），SQLAlchemy ORM → 改连接字符串 → PostgreSQL，业务逻辑代码不变。

## 六、其他关键选型

| 选型 | 选择 | 核心理由 |
|------|------|---------|
| **Web 框架** | FastAPI | 原生 async、自动 OpenAPI 文档、Pydantic 类型校验、SSE 流式支持 |
| **向量数据库** | ChromaDB | 嵌入式、零运维、支持 metadata 过滤、Python 原生 |
| **OCR 引擎** | MinerU（主）+ 百度 OCR（fallback） | MinerU 化学符号识别率 ~85%，百度 OCR 兜底 |
| **化学配平** | 自定义系数平衡算法 + RDKit | LLM 不可靠（~80%），确定性算法保证 100% 零误差 |
| **公式渲染** | KaTeX + mhchem | 唯一能正确渲染化学方程式的开源前端方案 |
| **容器化** | Docker（单容器） | 开发环境与生产环境一致，一键部署 |
| **Agent 检查点** | AsyncSqliteSaver（LangGraph） | 持久化对话状态，服务重启不丢失 |
| **LLM 上下文管理** | TrimMessages + LLM 摘要（`trim_context`） | 控制 token 消耗，P95 延迟 < 3s |
