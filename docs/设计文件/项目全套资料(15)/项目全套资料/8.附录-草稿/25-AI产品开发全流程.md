## 一、AI 产品开发与传统软件开发的根本区别

在进入具体流程之前，必须理解 AI 产品（尤其是 Agent 产品）为什么不能用传统软件开发的方法论：

| 维度 | 传统软件 | AI Agent 产品 |
|------|---------|-------------|
| **行为确定性** | 确定：同一个输入永远得到同一个输出 | 不确定：同一个 Prompt 两次调用可能不同 |
| **质量保障** | 单元测试覆盖逻辑分支 | 评测体系覆盖行为模式（统计性通过） |
| **需求表达** | "点击按钮 → 弹出对话框" | "当学生说'我不会'，Agent 应该反问而非给答案" |
| **Bug 来源** | 代码逻辑错误 | Prompt 设计、模型升级、工具 docstring 冲突 |
| **"完成"的定义** | 代码合并到 main 分支 | 对应评测场景通过率 ≥ 阈值 |
| **回归风险** | 改了 A 模块可能影响 B | 改了 Prompt A 可能让三个月前正常的场景失败 |
| **调试方式** | 断点 + 日志 | 工具调用轨迹 + 评测对比 |

这些区别决定了 AI 产品的开发流程必须围绕"评测"重建。

## 二、三阶段门控模型（3P 模型）

ChemAI 采用业界验证的三阶段门控模型：**Prototype → Pilot → Production**。每个阶段有明确的准入条件、退出标准和"kill criteria"（什么情况下终止项目）。

```
线索/想法
    │
    ▼
┌──────────────────────────────────────────────┐
│  Phase 1: Prototype（原型验证）               │
│  核心问题：AI 能不能做这件事？                  │
│  时间：1-2 周                                  │
│  投入：1 个工程师                              │
│  Kill Criteria：配平准确率 < 60%              │
│  退出标准：3/3 老师表示"会继续用"              │
└──────────────────┬───────────────────────────┘
                   │ ✅ 通过
                   ▼
┌──────────────────────────────────────────────┐
│  Phase 2: Pilot（试点验证）                   │
│  核心问题：真实场景下有没有价值？               │
│  时间：4-8 周                                  │
│  投入：全团队 3-4 人                           │
│  Kill Criteria：教师周活 < 40% 或诊断修正率 > 50% │
│  退出标准：教师批改时间减少 > 50% + 诊断采纳率 > 70% │
└──────────────────┬───────────────────────────┘
                   │ ✅ 通过
                   ▼
┌──────────────────────────────────────────────┐
│  Phase 3: Production（规模化生产）            │
│  核心问题：能否稳定、安全地服务更多用户？        │
│  时间：持续                                   │
│  投入：全团队                                  │
│  准入标准：安全层评测 100% + 路由层 > 85%      │
│             + 性能 P95 < 3s + 有回滚方案       │
└──────────────────────────────────────────────┘
```

### 2.1 阶段一：原型验证（Prototype）— 2026 年 3 月

**核心问题**：AI 能不能做化学教学这件事？

**做了什么**：
- 用一周时间搭建 LangGraph 最小可运行 Agent，只挂 3 个工具：`chemistry_tutor` / `search_exam_bank` / `balance_equation`
- 后端用 DeepSeek API（当时成本 ¥1/百万 token，极低）
- 前端只有一个对话界面——没有登录、没有数据库、没有多角色
- 找 3 位化学老师试用两天：给方程式让 AI 配平、问知识点让 AI 讲解、问高考真题让 AI 检索

**数据结果**：
- AI 配平化学方程式的准确率约 80%（当时没有四维审核引擎，纯靠 LLM 配平）
- 知识讲解没有明显错误（教研顾问人工审核，主观评估）
- 3/3 老师表示"会继续用"

**关键决策**：配平准确率只有 80%，但 3/3 老师都表示会用——这说明原型阶段的核心问题是"方向对不对"，不是"功能完不完美"。老师的原话是："就算只有 80% 的准确率，也比我手动批改快太多了——配平错误一眼就能看出来，我改一下就行。"

**如果失败了怎么办**：如果在原型阶段发现 AI 配平化学方程式的准确率只有 60%，项目就终止了。60% 准确率的产品不能进入学校——老师用两次出错就不再信任，而这个信任一旦失去就再也回不来了。**原型阶段的价值不是"做出什么东西"，而是"用最低成本得到 kill or continue 的信号"。**

**这个阶段的正确做法**：
- ❌ 花三周搭建完善的登录/权限/数据库系统 → 原型不需要
- ❌ 考虑前端用什么框架、后端用什么 ORM → 原型不需要
- ✅ 最小可用 + 找真实用户试用 + 快速判断方向

### 2.2 阶段二：试点验证（Pilot）— 2026 年 4-5 月

**核心问题**：在真实教学场景中，产品有没有价值？

**试点配置**：
- 长沙一所重点高中，高一化学组 3 位老师、2 个班（约 110 名学生）
- 完整的考试工作台：老师能出题、发布、学生在线作答、AI 诊断
- 跑了一个完整月——收集了真正的对比数据

**关键数据**：

| 指标 | 试点前 | 试点后 | 变化 |
|------|--------|--------|------|
| 教师批改+诊断时间/次考试 | 6 小时 | 45 分钟 | **-87.5%** |
| AI 诊断被教师直接采纳率 | — | 82% | — |
| 试点班月末对比测试平均分 | 基准 | +4.3 分 vs 对照班 | — |
| 学生练习完成率 | — | 76% | — |

**试点期间暴露出两个在原型阶段没发现的严重问题**：

1. **学生端 Agent 角色混乱**：Agent 会问"你是学生还是老师"——因为它没有 Persona 系统，不知道自己的身份。学生问"帮我配平这个方程式"，Agent 直接给答案而不是引导。

2. **ReAct 循环内容重复**：工具执行完返回结果后，LLM 会再说一遍同样的内容。比如工具返回 "配平结果: 4Fe + 3O2 = 2Fe2O3"，LLM 紧接着又输出"好的，配平结果是 4Fe + 3O2 = 2Fe2O3"——学生看到的是两遍同样的内容。

**试点阶段的退出标准（全部超额完成）**：
- ✅ 教师批改时间减少 > 50%（实际 87.5%）
- ✅ 诊断被教师直接采纳率 > 70%（实际 82%）
- ✅ 学生端完成率 > 70%（实际 76%）
- ✅ 无严重安全事故

**试点阶段的核心教训**：很多问题在原型阶段暴露不出来——原型只有 3 个人用、场景太窄。试点的价值在于用真实教学场景的压力测试暴露隐藏问题。如果跳过试点直接做"完整产品"，上面这两个问题就会在生产环境爆炸。

### 2.3 阶段三：规模化生产（Production）— 2026 年 6-7 月

**核心问题**：能否稳定、安全、可维护地服务更多用户？

**做了什么**：

1. **架构升级（v1 → v2）**：从 Coordinator + Router + 6 个 Sub-Agent 的多 Agent 架构，切换到单 Agent + 22 工具集 + Persona 过滤。路由准确率从 70-75% 提升到 85%+。

2. **建立评测体系**：14 维度评测体系（覆盖从工具路由到 Persona 隔离到 SSE 流式的全部维度），确定性评测 + API 评测双层架构

3. **实现 Persona 系统**：4 个角色（student/teacher/tutor/parent）的 YAML 配置 + TOOL_META 自动注册 + 评测自动验证隔离。彻底解决了试点阶段暴露的角色混乱问题。

4. **打通数据闭环**：教师端-学生端数据管道完全打通——教师发布考试 → 学生端接收 → 学生作答 → 自动批改 → 诊断入库 → 教师查看报告 → 布置针对性练习。

5. **答题卡 OCR 批改系统**：老师上传 30 张答题卡照片 → 百度 OCR 识别学号和答案 → LLM 语义批改 → 生成班级统计和个体诊断。整个流程 3 分钟。

6. **学生 Chat 覆盖高考 6 大考点**：离子方程式、物质的量、氧化还原、化学平衡、元素周期律、有机推断——每个考点有专属的 tutoring tool。

7. **Docker 容器化部署**：单机 SQLite WAL 模式，`docker compose up` 一键启动。

**Production 准入标准（全部通过）**：
- ✅ 功能层评测通过率 100%
- ✅ 安全层评测通过率 100%（Persona 隔离）
- ✅ 路由层评测通过率 > 85%
- ✅ 回归层评测通过率 100%
- ✅ 性能 P95 延迟 < 3s
- ✅ 有可执行的回滚方案（Docker 镜像版本控制）

## 三、评测驱动的开发节奏

### 3.1 为什么评测必须先行

传统软件开发："写完代码，测试通过，上线。"
AI Agent 开发：**"写完评测，确认它失败，写代码让它通过，上线，持续监控。"**

区别在于第一步——传统开发是"先写代码再写测试"，评测驱动是"先写评测再写代码"。为什么这个顺序如此重要？

**因为 Agent 的行为退化是无声的。** Prompt 没变、代码没变、工具没变——但 LLM 提供方悄悄升级了模型版本，导致之前正确的行为现在错了。如果没有评测，你只能在用户投诉后才知道——而且那时候你不确定是"偶发行为"还是"模型变了"。有了评测，CI 在 5 秒内告诉你。

**ChemAI 的一个真实案例**：2026-07-03，评测 RF-05（回归层——Agent 反复问角色身份）突然从通过变成失败。排查发现：新增了 `memory_student_get` 工具后，LLM 的 system prompt 中 Persona 信息被意外覆盖。如果没有回归评测，这个问题会在种子老师使用时才暴露。**评测在 CI 阶段就拦截了。10 分钟修复 vs 如果到生产环境可能影响一整天的教学。**

### 3.2 每一阶段的评测驱动

```
需求阶段：
  PM 不写"Agent 要能配平化学方程式"
  PM 写 evals 场景：
    "input: '配平 Fe + O2 = Fe2O3'
     assertions:
       - tool_called: balance_equation
       - param equation: 'Fe + O2 = Fe2O3'
       - response not_contains: 完整配平结果（应通过工具返回）"

开发阶段：
  工程师先写评测（确认评测失败——功能还没做）
  再写实现代码（确认评测通过）

验收阶段：
  不是 PM 点一下看看对不对
  而是跑完整评测套件——86+36 个全部通过才算完成

回归阶段：
  CI 自动跑全套评测
  任何维度通过率下降 > 5% → 触发告警
  路由层 < 75% → CI 阻断，不允许合入
```

### 3.3 迭代节奏

ChemAI 采用 2-4 周的迭代周期，具体取决于功能复杂度：

| 功能类型 | 示例 | 迭代周期 |
|---------|------|---------|
| 简单功能 | 加一个 tutoring tool | 1 周 |
| 中等功能 | 学生端练习页与教师端考试对接 | 2 周 |
| 复杂功能 | 答题卡 OCR 批改系统 | 4 周 |
| 架构变更 | v1→v2 Agent 架构升级 | 2 周（高密集） |

**一个标准迭代的结构**：

```
第 1 天：迭代计划
  输入：
    - 上一迭代评测报告（哪个维度下降了？哪个回归触发了？）
    - 教师反馈汇总
    - Product backlog 优先级
  输出：
    - 本次迭代功能清单（≤ 5 项核心功能）
    - 每个功能的评测场景定义
    - "完成标准"：对应评测场景 100% 通过

第 1-N 天：功能开发 + 评测编写
  - 工程师先写评测（让它失败）→ 写实现代码（让它通过）
  - 每个功能至少 3 个评测场景：正常路径、边界路径、错误路径
  - PM 检查评测场景是否覆盖真实用户场景

每天：10 分钟站会
  - 三个问题：昨天做了什么（关联评测编号）？今天做什么？有没有阻塞？
  - 禁止讨论技术细节——技术讨论会后另外安排

最后一天：迭代复盘（1-2 小时）
  - 评测数据：新增评测数、通过率变化、是否有退化的维度
  - 做对了什么：不是"完成了什么功能"，而是"哪些做法值得继续"
  - 做错了什么/下次怎么做：不是批斗会，是改进会
```

## 四、从线索到决定：需求发现与验证

### 4.1 线索来源

ChemAI 的起点是一条来自一线化学教师的反馈：

> "每次月考后我要花整整一个周末批改三个班的试卷——不是批对错，那个半天就完了，而是分析每道题学生的错误原因。这道题班上 35% 的人错了，但是为什么错？是概念没懂还是审题出错了？每个人原因不一样。我想给每个人不同的建议，但时间根本不允许。"

这条反馈包含了三个关键信息：
1. **明确的痛点**：批改+诊断耗时 6-10 小时/次考试
2. **具体的场景**：月考后的错因分析
3. **未被满足的需求**：想给每个人不同的建议，但时间不允许

### 4.2 验证方法

**不是"听到一个痛点就开工"**。进行三轮验证：

**第一轮：扩大样本（3→8 位教师深度访谈）**
- 确认痛点普遍性：8/8 教师表示"每次考试后的错因分析是最耗时的非教学工作"
- 发现额外痛点：5/8 教师提到"家长只问分数不关心错因"的问题——这后来成为家长端周报的产品定位

**第二轮：竞品能力缺口分析**
- 科大讯飞阅卷系统：能批量评分，不能化学错因诊断
- 作业帮/小猿搜题：能搜答案，不能诊断
- 学科网/组卷网：能组卷，不能动态诊断
- 结论：市面上没有产品回答"为什么错"这个问题

**第三轮：可行性验证（Prototype）**
- 一周搭建原型 → 3 位老师试用 → 100% 表示会继续用 → Go/No-Go 决策：Go

### 4.3 Go/No-Go 决策框架

| 维度 | 通过标准 | ChemAI 实际 |
|------|---------|-----------|
| 痛点真实性 | ≥ 5/8 受访者确认 | 8/8 ✅ |
| 技术可行性 | 原型核心能力达标 | 配平 80%，3/3 老师认可 ✅ |
| 市场空间 | TAM > 10 亿 | SAM 6.6-17.7 亿 ✅ |
| 团队能力 | 具备核心技术能力 | PM + AI 工程师 + 全栈 ✅ |
| 时机 | 有政策/市场窗口 | 双减后校内提质窗口 ✅ |

## 五、从决定到原型：MVP 设计原则

### 5.1 MVP 不是"功能最少的版本"

MVP 是"能验证核心假设的最少功能"。ChemAI 的核心假设是：

> **假设：化学老师愿意用 AI 工具诊断学生的错因，并且 AI 的诊断结果足够准确被采纳。**

验证这个假设不需要：
- ❌ 家长端（学生端还没验证，做什么家长端？）
- ❌ 自适应练习引擎（先验证诊断能力，再验证练习推荐）
- ❌ 真题关联系统（锦上添花，不是核心假设）
- ❌ 学校管理后台（一个试点学校不需要后台）

验证这个假设只需要：
- ✅ 答题卡批量上传 + OCR 识别
- ✅ AI 诊断每道错题的错误类型（概念/审题/表述）
- ✅ 班级诊断报告

### 5.2 先定义"好"的标准

ChemAI 在写第一行代码之前，先定义了"好"的标准：

```
化学出题：AI 生成的每道题必须经过四维安全审核
  ├─ 系数配平：100% 零误差（确定性算法保证，非 LLM）
  ├─ 反应条件：温度、压强、催化剂必须合理
  ├─ 产物预测：产物必须是化学上存在的
  └─ 危险品过滤：不出涉及危险品制备的题目

诊断结论：必须可被教师验证和修正
  ├─ 每项诊断附带推理依据
  ├─ 教师可一键"修正"诊断类型
  └─ 修正历史可追溯

安全红线（不可妥协）：
  ├─ Persona 隔离 100%：学生看不到教师工具
  ├─ 学生报告不展示排名（只展示个人进步）
  └─ 0 安全事故容忍
```

这些标准定义了"什么是不可接受的"。代码可以慢慢写，但这些红线碰都不能碰。

## 六、从原型到产品：关键架构决策

### 6.1 v1 → v2 Agent 架构升级

这是 ChemAI 开发过程中最大的一次架构变更：

**v1（Coordinator + Router + 6 Sub-Agent）**：
```
User → Coordinator → Router → Sub-Agent → Tool
                                  ├─ 出题专家（4 tools）
                                  ├─ 诊断专家（3 tools）
                                  ├─ 辅导专家（5 tools）
                                  ├─ ...
```
问题：Coordinator 路由准确率只有 70-75%。"离子方程式"请求经常被错误路由到"出题专家"而非"化学辅导"。

**v2（单 Agent + 22 tools + Persona 过滤）**：
```
User → ReAct Agent (看全部 25 个工具 → 自己选) → Tool
```
改进：路由准确率 70-75% → 85%+。去掉 Coordinator 和 Router 两个节点的延迟。Persona YAML 过滤替代硬编码的工具分配。

**决策过程**：
1. 评测数据说话：对比 v1 和 v2 在相同 32 个路由场景上的准确率
2. v2 在所有维度上不低于 v1，在路由延迟上显著优于 v1
3. 保留 v1 代码作为 fallback（但不推荐使用），降低风险

### 6.2 其他关键决策

| 决策 | 选项 | 选择 | 原因 |
|------|------|------|------|
| Agent 框架 | LangGraph vs 自研 vs CrewAI | LangGraph | 社区成熟 + checkpoint 持久化 + SSE 流式 |
| 数据库 | PostgreSQL vs SQLite | SQLite + WAL | 单校部署不需要分布式，零运维成本 |
| 对话持久化 | InMemorySaver vs AsyncSqliteSaver | AsyncSqliteSaver | 服务重启不丢对话，多请求共享状态 |
| LLM Provider | 单 Provider vs 多 Provider | 多 Provider 路由 | MiMo→DeepSeek→通义千问→GLM 四级 fallback |
| 前端框架 | React/Vue vs Vanilla JS | Vanilla JS + Vite | 页面少（教师端 5 页 + 学生端 4 页），框架必要性低 |
| Persona 管理 | 硬编码 vs YAML 配置 | YAML | 加角色不改代码，评测自动验证隔离 |

## 七、上线策略与风险控制

### 7.1 灰度发布

```
新功能开发 + 评测通过
  → 开发环境验证（全套评测）
  → 1 所种子学校试用 3 天
  → 3 所学校试用 1 周
  → 全量推送
```

每次扩展前检查：错误率、P95 延迟、评测通过率、教师反馈。

### 7.2 回滚条件

以下任何条件触发 → 立即回滚到上一个稳定 Docker 镜像：
- 安全层评测（Persona 隔离）通过率 < 100%
- 路由层评测通过率下降 > 10%
- 生产环境 P95 延迟 > 10s（持续 5 分钟）
- 任何 P0 级事故

### 7.3 监控指标

| 指标 | 正常范围 | 告警阈值 |
|------|---------|---------|
| SSE 流断开率 | < 1% | > 5% |
| 工具调用失败率 | < 5% | > 10% |
| P95 延迟 | < 3s | > 5s |
| 评测通过率 | ≥ 阈值 | < 阈值 |
