# 架构决策记录 — ChemAI 关键技术选择

> 架构决策记录（ADR）记录 ChemAI 开发过程中的关键技术选择及其上下文、理由和后果。每个 ADR 回答三个问题：我们面临什么选择？我们选了哪个？为什么？

## ADR-001: 选择单 Agent + 工具集架构而非多 Agent

**日期**: 2026-05-25
**状态**: 已采纳
**影响范围**: Agent 层核心架构

**背景**: ChemAI 最初（v1）采用了 Coordinator + Router + 6 个 Sub-Agent 的多 Agent 架构：

```
v1 架构：
User → GuardState → Coordinator → Router → Sub-Agent → Tool
                                              ├─ 出题专家（4 tools）
                                              ├─ 诊断专家（3 tools）
                                              ├─ 辅导专家（5 tools）
                                              ├─ 批改专家（3 tools）
                                              ├─ 搜索专家（2 tools）
                                              └─ 通用专家（3 tools）
```

每个 Sub-Agent 有独立的 Prompt 和工具集，Coordinator 负责把用户请求路由到正确的 Sub-Agent，Router 负责在 Sub-Agent 内部选择具体工具。

**决策**: 替换为 v2 单 Agent 架构——一个 ReAct Agent 看到全部 25 个工具，由 LLM 根据工具的 `docstring` 自行选择。通过 Persona YAML 配置限制每个角色可见的工具集。

```
v2 架构：
User → GuardState → ReAct Agent（看全部 25 个工具 → 自己选）→ Tool
```

**理由**:

1. **路由准确率**：v1 的 Coordinator 路由准确率约 70-75%——经常把"离子方程式"请求错误路由到"出题专家"而非"化学辅导"。v2 让 LLM 自己选工具，准确率提升到 85%+。评测数据（32 个路由场景对比）直接驱动了这个决策。

2. **延迟降低**：v1 每条请求经过 Coordinator（1 次 LLM 调用）+ Router（1 次 LLM 调用）= 至少 2 次 LLM round-trip。v2 只有 1 次 LLM 调用。P50 延迟从 ~3s 降到 ~1.5s。

3. **维护成本**：v1 添加新功能需要同时修改 Coordinator Prompt + 对应 Sub-Agent Prompt + Router 逻辑。v2 只需加一个 tool 并在 TOOL_META 中声明 personas。

4. **工具发现**：v1 的 Sub-Agent 只能看到分配给它的一小部分工具——如果学生的问题需要跨 Sub-Agent 的工具协作，Coordinator 无法处理。v2 模型看到所有工具，可以自行组合。

**后果**:
- v1 代码保留在 `agent/langgraph_agent.py` 作为 fallback，但不推荐使用
- 所有新功能在 v2（`agent/langgraph_agent_v2.py`）上开发
- Persona YAML 替代了硬编码的工具分配逻辑
- 评测体系同步更新——路由准确率场景从 v1 的 Coordinator 路由测试变为 v2 的工具选择测试

## ADR-002: 选择 AsyncSqliteSaver 而非 InMemorySaver 做对话持久化

**日期**: 2026-07-04
**状态**: 已采纳
**影响范围**: Agent 对话状态管理

**背景**: v2 Agent 最初使用 LangGraph 的 `InMemorySaver` 作为 checkpointer。发现了两个严重问题：

1. **服务重启丢失所有对话**：InMemory = 进程内存。uvicorn 重启 → 所有学生的对话历史消失。
2. **不同请求不共享状态**：第一个 HTTP 请求创建 Agent A → 写入状态到 A 的 saver。第二个 HTTP 请求创建 Agent B → B 的 saver 是空的 → 学生发现"AI 不记得刚才说了什么"。

**决策**: 改用 `AsyncSqliteSaver`，存储到 `chemai_checkpoints.db`。v1 和 v2 共享同一个全局单例 saver 实例。

**理由**:
- SQLite 持久化 → 服务重启不丢对话
- 全局单例 → 不同请求、不同 Agent 实例共享同一个状态库
- WAL 模式 → 支持多读者并发读取
- 与 v1 saver 复用 → 一个 DB 文件管理所有对话
- LangGraph 原生支持 AsyncSqliteSaver，集成成本极低（改一行 import）

**后果**:
- `chemai_checkpoints.db` 文件随时间增长 → 需要 `trim_context` 管理对话历史长度（超过 30 条触发 LLM 摘要压缩）
- 每月需要 VACUUM 回收已删除 checkpoint 的磁盘空间
- WAL 模式下写操作串行化 → 高并发场景可能需要引入连接池或迁移到 PostgreSQL

## ADR-003: 选择评测驱动开发而非功能驱动开发

**日期**: 2026-06-01
**状态**: 已采纳
**影响范围**: 全项目开发流程

**背景**: 化学 Agent 的行为具有高度不确定性——同一个问题，LLM 可能回答、可能反问、可能调错工具。传统 QA（"测一下看对不对"）无法覆盖这种多样性。在 2026 年 5 月的试点中，多次出现"这周好好的功能下周就坏了"的情况——不是代码被改了，而是 LLM 提供方升级了模型版本。

**决策**: 建立 14 维度评测体系。每个功能在开发前先定义 evals 场景。CI 门禁根据评测通过率自动阻断或放行。评测分两层：确定性评测（不调 LLM，纯代码断言，86 个场景，< 5 秒）和 API 评测（调 LLM 验证行为，36 个场景，~2 分钟）。

**理由**:
- Agent 的行为退化无法通过 code review 发现——Prompt 没变、代码没变、模型悄悄变了
- 评测体系是唯一能回答"这个改动安全吗"的机制——尤其是在改 Prompt 或升级模型版本时
- 从 2026-07-01 到 07-04，评测数量从 41 增长到 86（确定性）+ 36（API），线上事故率从每周 2-3 次降到 0

**后果**:
- 新功能需要写评测 → 开发周期看似变长（实际减少了调试和线上修复的时间）
- 评测代码需要维护 → 评测腐烂 = 产品质量没有保障
- 评测覆盖诚实原则：未触发的场景报告为 `null`，不是 `100%`

## ADR-004: 选择 SQLite + WAL 而非 PostgreSQL

**日期**: 2026-04-14
**状态**: 已采纳
**影响范围**: 数据持久化层

**背景**: ChemAI 面向单学校部署（同时在线 < 50 人），写操作频率低（主要是考试提交和诊断写入），读操作占比高。

**决策**: SQLite + WAL 模式 + `check_same_thread=False`。所有表通过 SQLAlchemy ORM 定义，数据库层对上层代码透明。

**WAL 模式配置**:
```python
PRAGMA journal_mode=WAL;       # 写前日志，支持读写并发
PRAGMA synchronous=NORMAL;      # 平衡安全与性能
PRAGMA foreign_keys=ON;         # 外键约束
PRAGMA cache_size=-8000;        # 8MB 缓存
PRAGMA busy_timeout=5000;       # 5s 锁等待超时
```

**理由**:
- 零运维成本——不需要单独安装和配置数据库服务
- WAL 模式支持读写并发（读者不阻塞写者，写者不阻塞读者）
- Docker 单容器部署（应用 + DB 在一起，一个 `docker compose up` 全启动）
- SQLAlchemy ORM 抽象了数据库层 → 当并发达到瓶颈时迁移到 PostgreSQL 只需改连接字符串和少量 SQL 方言差异

**不选择 PostgreSQL 的理由**: 一个部署给学校的本地化工具，不需要分布式数据库。运维一个 PostgreSQL 实例的成本（安装、备份、升级、故障恢复、监控）远超 ChemAI 现阶段的实际需求。**等到有 50+ 所学校同时在线再迁移，ROI 才对。**

**后果**:
- 写锁争用 → WAL 模式 + `busy_timeout` 已缓解
- 数据库文件大小随时间增长 → 定期 VACUUM
- 缺少 PostgreSQL 的一些高级功能（如 JSONB 索引、全文搜索）→ 这些功能对当前阶段不重要

## ADR-005: 选择 LangGraph 而非自研 Agent 框架

**日期**: 2026-04-14
**状态**: 已采纳
**影响范围**: Agent 框架选型

**背景**: 2026 年有多个 Agent 框架可选：LangGraph（LangChain 生态）、CrewAI（多 Agent 协作）、AutoGen（微软）、自研。

**决策**: 使用 LangGraph 的 `create_react_agent` 作为 Agent 框架。

**理由**:
- **社区成熟度**：LangGraph 是 LangChain 生态的核心组件，文档完善，社区活跃
- **Checkpoint 持久化**：`AsyncSqliteSaver` 开箱即用，不需要自己写对话状态管理
- **SSE 流式输出**：`astream_events` 提供标准的事件流接口，token-level streaming
- **ReAct 模式内置**：`create_react_agent` 封装了 Thought → Action → Observation 循环
- **v1→v2 平滑迁移**：`create_react_agent` 替换 Coordinator+Router 架构只需改一行代码
- **放弃自研**：自研 Agent 框架需要 2-3 个月投入，且需要处理 checkpoint、streaming、error recovery 等 LangGraph 已经解决的问题。ROI 不匹配

**不选择 CrewAI/AutoGen**: 这些框架更偏向多 Agent 协作和角色扮演。ChemAI 的核心需求是工具调用的准确率，不是 Agent 之间的对话。

**后果**:
- 依赖 LangGraph 的版本更新和 breaking changes
- 框架的抽象层在极端性能场景下可能有开销 → 当前并发量下不是瓶颈
- 如果未来需要更底层的控制（如自定义 ReAct 循环），可能需要绕过 `create_react_agent` 直接用 `StateGraph`

## ADR-006: 选择 Persona YAML 配置而非硬编码角色

**日期**: 2026-07-03
**状态**: 已采纳
**影响范围**: 角色管理和工具过滤

**背景**: 最初每个角色（学生/教师/家长）的工具集和 Prompt 是硬编码在 Python 代码里。学生和教师的差异散落在 `langgraph_agent_v2.py`、`tools_core.py`、前端 API 等多个文件中。加一个新角色意味着改 4-5 个文件。

**决策**: 集中到 `agent/personas/*.yaml`。结构如下：

```yaml
# agent/personas/student.yaml
name: student
display_name: 化学助教（学生版）
system_prompt: |
  你是一个高中化学 AI 助教，正在帮助一位高中生学习化学。
  核心理念：引导学生自己推导出答案，不直接给答案。
  ...
available_skills:
  - chemistry_tutor
  - simulate_experiment
  - web_search
  - ionic_equation_tutor
  - stoichiometry_tutor
  - redox_tutor
  - equilibrium_tutor
```

TOOL_META 中每个工具声明自己属于哪些角色：
```python
TOOL_META = {
    "balance_equation": {
        "personas": ["teacher", "tutor"],  # 学生和家长不可见
        "call_limit": 5,
    },
    ...
}
```

Agent 创建时，取 Persona YAML `available_skills` 和 TOOL_META `personas` 的**交集**，自动过滤。

**理由**:
- 加一个新角色 → 新建一个 YAML 文件，不改任何代码
- 调一个角色的 system_prompt → 改 YAML，不需要重启服务（hot reload）
- 角色权限审计 → 打开 YAML 一眼就能看出哪个角色有哪些工具
- 评测验证 → 可以写自动化断言："student persona 的可用工具集不应包含 balance_equation"
- `test_yaml_skills_all_in_auto` 评测自动验证 YAML 文件与 TOOL_META 的一致性

**后果**:
- YAML 文件的 `available_skills` 需要和 TOOL_META 的 `personas` 字段保持同步
- 新加工具时开发者需要同时更新 TOOL_META（声明 personas）和对应的 Persona YAML（声明 skills）——这是两步操作，容易遗忘
- 评测 `test_yaml_skills_all_in_auto` 在 CI 中自动捕获不一致

## ADR-007: 选择 tutoring tool 工厂模式

**日期**: 2026-07-04
**状态**: 已采纳
**影响范围**: 化学辅导工具开发

**背景**: 7 个化学辅导工具（`ionic_equation_tutor`、`stoichiometry_tutor`、`redox_tutor`、`equilibrium_tutor`、`periodic_law_tutor`、`organic_tutor`、`chemistry_tutor`）有完全相同的三分支结构：

```
有输入（学生提交了答案）→ 给反馈（对/错 + 引导）
学生回复 → 给下一步引导
没有输入（学生刚打开）→ 给知识点介绍和初始问题
```

如果不做抽象，7 个工具 = 7 × 60 行 = 420 行几乎相同的代码。任何引导逻辑的改变需要改 7 个地方。

**决策**: 提取 `_make_tutor_tool(skill_name, display_name, intro_message, ...)` 工厂函数。每个新 tutoring tool 只需 15 行配置：

```python
def _make_tutor_tool(
    skill_name: str,
    display_name: str,
    chapter: str,
    intro_template: str,
    feedback_template: str,
) -> Tool:
    """工厂函数：创建标准 tutoring tool"""
    async def tutor_func(input_text: str = "") -> str:
        if not input_text:
            return intro_template  # 分支1：初始引导
        # 分支2：分析学生回答 + 分支3：给反馈和下一步
        ...
    return Tool(name=skill_name, description=..., func=tutor_func)
```

**理由**:
- 代码量：7 个工具从 400+ 行缩减到 100+ 行配置
- 改引导逻辑 = 改工厂函数一处 → 7 个工具全部受益
- 加新 skill → 复制 15 行配置，不需要理解三分支逻辑
- 评测工厂输出 → 一个 `@pytest.mark.parametrize` 覆盖所有 tutoring tool 的行为验证

**后果**:
- 所有 tutoring tool 有统一的行为模式 → 学生体验一致（不管在哪个考点，引导风格相同）
- 如果需要"不同考点不同引导风格" → 需要在工厂函数中引入 override 机制（当前不需要）
- 后续添加 `periodic_law_tutor` 和 `organic_tutor` 各只用了 10 分钟

## ADR-008: 选择单端口 Docker 部署

**日期**: 2026-07-04
**状态**: 已采纳
**影响范围**: 部署架构

**背景**: 开发环境遇到多进程抢 8000 端口的问题——4 个 uvicorn worker 进程同时监听同一端口，导致请求随机落到旧代码实例上。排查了 2 小时才发现是上一个 uvicorn 进程没有正常退出。

**决策**: Docker 单容器部署。FastAPI 绑定 `0.0.0.0:8000`。前端 Vite build 输出由 FastAPI `StaticFiles` 中间件直接 serve。生产环境单端口，无 CORS 跨域。

```
docker compose up -d  →  一键启动
docker compose down    →  彻底清理（不会遗留僵尸进程）
```

**理由**:
- Docker 提供进程隔离 —— 容器停了 = 端口释放，彻底解决僵尸进程问题
- `depends_on` 保证启动顺序
- 单端口 → 不需要 CORS 配置 → 减少安全面
- 后续扩容只需 `docker compose scale chemai=3` + Nginx load balancer

**不选择多 worker 的理由**: ChemAI 的并发量低（< 50 同时在线），单 worker + async FastAPI 完全够用。多 worker 引入的进程间状态同步问题（如 checkpoint 共享）远超其带来的吞吐提升。

**后果**:
- 单 worker 意味着如果进程卡住（如 LLM 调用超时），整个服务阻塞
- 需要合理设置 `uvicorn --timeout-keep-alive` 和 LLM 调用的超时时间
- 规模化阶段需要引入 Nginx + 多容器

## ADR-009: 选择多 Provider LLM 路由而非单 Provider

**日期**: 2026-06-15
**状态**: 已采纳
**影响范围**: LLM API 调用

**背景**: 国内 AI 厂商的 API 稳定性参差不齐——DeepSeek 偶尔维护（通常 2-4 小时），通义千问偶发 429 限流，小米 MiMo 的 API 还在 beta 阶段。依赖单一 Provider = 服务可用性 ≤ 该 Provider 的可用性。

**决策**: 四级 Provider fallback 路由：

```python
PROVIDER_PRIORITY = [
    ("mimo",       "moonshot-v1-8k"),    # 首选（成本最低，¥0.8/百万 token）
    ("deepseek",   "deepseek-chat"),      # 主力（性价比最优）
    ("dashscope",  "qwen-turbo"),         # 第一 fallback
    ("zhipu",      "glm-4-flash"),        # 第二 fallback
]
```

Fallback 触发条件：
- API 5xx → 立即切换
- 超时 > 30s → 降级切换
- 429 限流 → 等待 5s 重试 1 次，仍失败则切换
- 连续失败 3 次 → 标记 Provider 为"不可用"，15 分钟后自动重试

**理由**:
- 月度 API 成本 < ¥200（大部分请求走 MiMo 和 DeepSeek）
- 任意一个 Provider 可用即可保证服务不中断
- 不同 Provider 的模型能力在化学教学场景下差异不大（都是通用 LLM，不做化学专项 fine-tune）

**不选择 GPT-4/Claude**: 成本高（¥40-80/百万 token）、延迟大（国际网络）、国内学校数据合规风险（数据出境）。

**后果**:
- 同一请求在不同 Provider 上的行为可能有差异 → 评测需要在主力 Provider (DeepSeek) 上运行
- Provider 的模型版本升级可能导致行为变化 → 评测体系定期重跑全套场景

## ADR-010: 选择 Context Trim 混合策略（滑动窗口 + LLM 摘要）

**日期**: 2026-07-04
**状态**: 已采纳
**影响范围**: Agent 对话上下文管理

**背景**: 化学辅导对话可能非常长——学生反复追问、AI 引导多轮、调试配平步骤。每轮对话的完整历史都保存在 checkpoint 中。如果不裁剪：
- Context 越来越长 → LLM 延迟越来越高 → P95 超过 5s
- Token 消耗指数增长 → API 成本失控
- 过长 context 导致 LLM 注意力分散 → 路由准确率下降

**决策**: 三层混合裁剪策略（`agent/context_manager.py`）：

```
无条件保留：最后 6 条消息（近期上下文对辅导对话最重要）
      +
有条件保留：包含关键字的消息（"配平"、"离子方程式"、"不会"、"步骤"等）
      +
LLM 摘要压缩：超过 30 条时触发，将前 24 条压缩为一段简短摘要

结果：context 长度控制在 ~15-20 条消息等效范围内
```

**理由**:
- 无条件保留最后 6 条 = 保证当前辅导流程的上下文连续
- 关键字过滤 = 保留跨越多轮的重要信息（如学生反复卡在同一个知识点）
- LLM 摘要 = 保留对话的"主题连续性"而不保留逐字记录
- 30 条阈值来自实际数据：绝大多数辅导对话在 20 轮内完成，化学辅导极少超过 30 轮

**后果**:
- LLM 摘要可能丢失精确的化学式或数值 → 摘要 prompt 特别强调"保留所有化学式和数值"
- 摘要本身消耗 token → 但远小于保留完整历史（摘要 200 token vs 完整历史 5000+ token）
- 学生在多轮后提到"刚才那个方程式" → 摘要中保留了方程式，Agent 可以响应

## ADR-011: 选择 TOOL_META 自动注册 + 评测验证

**日期**: 2026-07-04
**状态**: 已采纳
**影响范围**: 工具管理和 Persona 一致性

**背景**: 随着工具数量从 3 个增长到 22 个，手动维护工具列表和角色分配变得越来越容易出错。v1 时期加一个工具要改 4 个地方：工具函数文件 + Router Prompt + Coordinator Prompt + Persona 过滤逻辑。漏掉任何一步都会导致工具"存在但不可用"或"不该有的角色能用"。

**决策**: 每个工具在 `TOOL_META` 中声明自己的元数据：

```python
TOOL_META = {
    "balance_equation": {
        "personas": ["teacher", "tutor"],
        "call_limit": 5,
        "approval_required": False,
    },
    "assign_adaptive_practice": {
        "personas": ["teacher"],
        "call_limit": 3,
        "approval_required": True,  # 破坏性操作
    },
}
```

Agent 创建时通过 persona 名称自动过滤工具集。评测 `test_yaml_skills_all_in_auto` 自动验证 Persona YAML 与 TOOL_META 的一致性。

**理由**:
- 工具定义和角色分配在同一处 → 不会出现"工具写了但忘了注册角色"的情况
- 评测自动验证一致性 → CI 能在 5 秒内发现配置不一致
- `call_limit` 防止 LLM 陷入无限循环调用同一个工具
- `approval_required` 标记破坏性操作 → GuardState 自动拦截并要求用户确认

**后果**:
- 新加工具时必须同步更新 Persona YAML 的 `available_skills` 和 TOOL_META 的 `personas` → 两步操作
- 如果开发者忘了更新 Persona YAML，评测会在 CI 中捕获（YAML 列表 ⊆ TOOL_META 声明）
- 如果开发者忘了更新 TOOL_META，工具对任何角色都不可见 → 功能测试会失败

## ADR-012: 选择 Vanilla JS + Vite 而非 React/Vue

**日期**: 2026-04-20
**状态**: 已采纳
**影响范围**: 前端技术选型

**背景**: 前端页面少且结构简单——教师端 5 个页面（考试工作台、诊断面板、学生管理、OCR 上传、学情仪表盘）+ 学生端 4 个页面（对话、练习、错题本、报告）。没有复杂的客户端状态管理需求（状态主要在后端和数据库）。

**决策**: Vanilla JavaScript + Vite（构建工具）+ 自定义 Web Components。

**理由**:
- 页面数量少（< 10 个），React/Vue 的组件化收益有限
- Vite 提供开箱即用的 HMR、build、proxy（`/api` → `localhost:8000`）
- 框架的学习成本和构建复杂性 > 当前规模下的收益
- 团队规模小（1 个全栈工程师），不需要为框架约定而增加沟通成本
- 随着产品增长，如果页面数量超过 20 个，可以渐进式引入 React

**不选择 React/Vue 的理由**: 不是为了"反框架"，而是当前产品阶段的 ROI 不匹配。一个 5 页面的教师端引入 React = 多 200KB JS bundle + 组件抽象 + 状态管理选型 + 路由库——而实际上所有"状态"都在后端。

**后果**:
- 前端代码组织需要自律（没有框架强制的文件结构）
- 交互复杂的页面（如考试工作台 71KB `exam-v2.html`）代码量较大
- 如果页面数量增长到 20+，迁移到 React 的成本需要考虑——但当前不着急
