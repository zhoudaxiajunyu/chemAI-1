# 31. 评测体系设计

> 产品设计文档 | ChemAI 智辅化学 | 设计阶段
> 说明：本文档为评测体系**完整版蓝图**（L0-L6 七层 + 判官五族 + 快慢双轨）；实现层采用简化落地，与本文档的分层关系详见《52-Evals评测体系搭建》。

---

## 一、评测体系定位

评测体系是 ChemAI Agent 的**质量基础设施**，承担四个目标（按优先级）：

| 目标 | 回答的问题 | 运行方式 |
|------|-----------|---------|
| **发布门禁** | 这次更新能不能发？ | 每次更新前跑，不合格就拦下 |
| **质量度量与趋势** | Agent 变好还是变差？ | 持续跑、出趋势 |
| **指导迭代** | 下一步该开发什么？ | 评估先行，发现薄弱点驱动开发 |
| **对标同行** | 我们的 Agent 处于什么水平？ | 二期接外部 benchmark |

评测体系要回答产品的三个问题：**基本能力能跑吗（确定性）→ Agent 聪不聪明（语义质量）→ 会不会静默退化（回归）**。传统"功能测试清单"只能回答第一个，评测体系把三个都覆盖。

## 二、七层评估模型（L0-L6）

评测体系按"评估对象"分为七层，每层回答一个问题：

| 层 | 评估什么 | 回答的问题 | 机制 | 运行层 |
|:---:|---------|-----------|------|:---:|
| **L0** | 工具自身正确性 | 每个工具干得对不对？ | 确定性断言 | 快跑 |
| **L1** | 行为轨迹 | 该用哪个工具、参数对不对、顺序对不对？ | 确定性断言（黄金场景） | 快跑 |
| **L2** | 输出与交互质量 | 答案对不对、交互聪不聪明？ | LLM-as-judge + 五族 rubric | 慢跑 |
| **L3** | 安全护栏 | 会不会被注入、越权、逃逸？ | 对抗语料 + 断言 | 慢跑 |
| **L4** | 性能预算 | 延迟、token、循环数超预算吗？ | 阈值断言（软警告起步） | 快跑 |
| **L5** | 稳定性回归 | 修过的 bug 回来了吗？ | 快照对比、回归集 | 快跑 |
| **L6** | 端到端任务 | 完整任务能跑通吗？ | 场景剧本 + 成功判定 | 慢跑 |

**为什么是七层**：旧的三分法（基线/边界/回归）缺少两层关键能力——**L2 判官层**（不评估答案质量与交互智能，就无法回答"Agent 聪不聪明"）和 **L0 工具自身正确性**（工具被改坏时无法被第一时间拦截）。七层的每一层都对应一个独立的评估机制与运行节奏，层与层之间不互相替代。

**层间关系**：L0/L1 是"能力地基"（确定性、零成本、每次必跑）；L2/L3 是"质量与安全"（语义判断与对抗，花 token）；L4/L5 是"防退化"（性能与回归）；L6 是"业务验证"（完整闭环）。

## 三、快/慢双层运行

七层按**成本与耗时**归入两层运行模式：

| 轨道 | 组成 | 触发时机 | 成本 | 门禁语义 |
|------|------|---------|------|---------|
| **快跑层** | L0 + L1 + L4 + L5 | 每次更新/提交（CI） | 零 LLM 成本，秒级 | **100% 必须绿**——确定性断言，挂了就是真挂了 |
| **慢跑层** | L2 + L3 + L6 | 夜间 / 发布前 | 分钟级，花 token | **严重错误一票否决**；分数只做趋势 |

**快跑层**：开发者每次更新跑 `python evals/run_evals.py --fast`（秒级、零 LLM 成本），CI 用同一命令拦截坏 PR。快跑层当前 93 个确定性用例，实测约 77 秒完成。

**慢跑层**：发布负责人跑 `python evals/run_evals.py --slow`（分钟级、花 token），得到区分"严重错误（拦发布）"与"分数（仅趋势）"的报告。慢跑层载体为夜间定时 + 发布前手动触发。

**运行器设计**：
- 层注册表：把七层映射到测试模块与运行层，新增测试只需登记一行（数据即代码）
- 空层占位：未实现的层在报告中如实标注"未实现"，不填充空结果
- 报告：按层分组，每条结果带 severity（pass / warn / fail / severe）与层标签
- 趋势：报告按时间戳归档，历史序列（index.json）回答"Agent 变好还是变差"
- 成本台账：报告内嵌判官调用次数与预估费用（¥），月度预算 ¥500 内可控

## 四、门禁策略

### 4.1 两级门禁

| 轨道 | 规则 |
|------|------|
| 快跑层 | **100% 必须绿**——任一确定性失败 → 阻止合并（exit 非零） |
| 慢跑层 | **严重错误一票否决**——化学错误、安全问题、端到端失败 → 拦发布；普通失败与告警只入报告与趋势 |

**为什么慢跑层不用分数线门禁**：判官分数有噪声（LLM 打分的固有波动），用分数拦发布会误伤；所以分数只做趋势，真正拦发布的是"严重错误"（severe 级结果）。

### 4.2 评估先行机制（expected_fail）

评估即 spec：先写评估定义"什么算好"，此时评估必然全红。红评估用 `expected_fail` 标记声明"我现在就该红"：

| 标记 | 实际结果 | 处理 |
|------|---------|------|
| 有标记 | 红 | 计为 pending（豁免），不进失败统计，不挡门禁 |
| 有标记 | 绿 | 通过但醒目标记"功能可能已完成，请移除标记转常驻" |
| 无标记 | 红 | 失败，进失败统计 |

这让评估先行工作流不会让门禁从第一天起全红，同时不会出现"默默变绿但仍在豁免名单里"的死标记。

### 4.3 覆盖诚实

- 未触达/未实现的层报告为"未实现"或"未触达"，**不**以 0/0 冒充 100%
- 未测量的指标保持"未测量"（如 token 读数不可用时不填默认值）
- 判官低置信度/低分样本自动进入人工复核队列，只有判官自信的部分才自动计入门禁

## 五、L2 判官库：五族 rubric

### 5.1 为什么需要判官

确定性断言只能回答"调了哪个工具、参数对不对"，回答不了"agent 出的题化学对不对、交互聪不聪明"。判官（LLM-as-judge）按能力族打分，把**答案质量与交互质量**纳入评估。

### 5.2 五族 rubric

| 族 | 判官评什么 | 评分维度要点 |
|----|-----------|-------------|
| **出题** | 生成的题目质量 | 化学正确性（权重最高）+ 难度匹配 + 解析正确 + 格式规范 |
| **判卷** | 批改判定质量 | 每题判分对错（vs 黄金答案） |
| **诊断** | 障碍分类质量 | 障碍类型判断（concept / reading / expression） |
| **方案** | 学习计划质量 | 适配性 + 可执行性 + 个性化 |
| **交互智能** | 对话交互质量 | 澄清追问、主动推荐、给选项引导、拆解与进度 |

评分契约：分数 0-100 + 置信度（low / medium / high）+ rationale（判定理由）+ severe_flags（严重错误标记）。

### 5.3 判官设计要点

1. **判官与主模型解耦**：判官用备选 provider（与被评模型不同），避免"自己给自己打分"的自评偏差；上线前先用真题 vs 官方答案**实测判官能力**。
2. **校准门槛（族粒度）**：每族 20-30 条人工标注样本构成校准集，判官 vs 人工一致率 ≥ 80% 的族才启用自动计分；不达标的族自动走"判官 + 人工复核"的**人机混合**模式。**启用决定在族粒度，不是全局开关。**
3. **校准数据源**：出题/判卷族用题库真题 + 官方答案；诊断/方案族用项目历史诊断数据（人工已标注样本）；交互智能族用真实"蠢场景"翻译的黄金场景。
4. **人机混合兜底**：confidence=low 或低分临界区的样本自动抽入人工复核队列；复核结果回写样本库用于下次校准。
5. **成本控制**：单次慢跑判官调用硬上限 200 次（超出截断并标注"未测样本 N 条"）；单次调用约 ¥2-5，月度预算 ¥500 内可控。
6. **与门禁的关系**：判官分数**永不进门禁**；判官输出的 severe_flags（化学错误、安全问题）由慢跑层否决逻辑消费。

## 六、评估先行（eval-first）工作流

**评估即 spec，先写评估再开发**：

```
对每个开发项：
  1. 先写它的评估场景（定义"什么算好"）——此时全红，用 expected_fail 豁免
  2. 开发到绿
  3. 移除 expected_fail 标记，转快/慢跑层常驻
```

红 → 绿的过程本身就是开发进度指标。这个工作流驱动了三项开发（均为完整案例）：

**A. 基础工具四件套**（read / write / edit / bash 沙箱 + find / grep）：
- L0 评估先行：read（编码处理/路径穿越/敏感文件拒绝）、edit（精确替换/找不到明确报错）、bash（沙箱逃逸/危险命令/超时）
- L3 同步扩：bash 注入（`;`、`&&`、`$()`、重定向）、危险命令拦截、跨目录访问
- 沙箱形态：工作目录锚定 + 命令白名单 + 超时（30s）+ 输出截断（8KB）+ 列表参数调用（机制上消除注入面）

**B. 出题智能化**：交互智能黄金场景先行——"我要出题"必须追问题型/难度/知识点 + 按班级薄弱点推荐（含依据可见），然后做 persona/prompt 增强与薄弱点上下文注入。

**C. planner 接线 + L6 端到端**：复杂任务拆解为步骤计划并汇报进度（SSE 步骤卡），端到端场景剧本验证完整任务成功率。

## 七、黄金场景体系

### 7.1 场景结构

每个黄金场景 = **输入 + 期望行为断言**：

```yaml
- id: wf-search-then-generate
  input: "先去题库里找关于电化学的真题，参考它们出3道新题"
  assertions:
    - {type: tool_called, tool: search_exam_bank}
    - {type: tool_called, tool: generate_questions}
    - {type: tool_trajectory_order, tools: [search_exam_bank, generate_questions]}
    - {type: tool_count, lte: 8}
    - {type: no_error}
```

### 7.2 断言类型体系

| 分组 | 断言 | 说明 |
|------|------|------|
| 工具调用 | `tool_called` / `not_tool_called` | 必须/禁止调用某工具 |
| | `tool_arg_contains` | 工具参数包含指定键值 |
| | `tool_count` / `max_tool_calls` | 调用次数上限 |
| | `tool_trajectory_order` | 工具调用顺序（子序列匹配） |
| 行为结果 | `no_error` / `has_text_response` | 无错误 / 必须有文本回复 |
| | `text_contains_one_of` | 回复包含指定文案之一 |
| | `interrupt_triggered` | 审批中断被触发 |
| | `route_assertion` | 页面路由断言 |
| 稳定性 | `tool_set_stable` / `tool_order_stable` | 重复运行工具集/顺序稳定（含阈值） |
| | `trajectory_hash_stable` | 轨迹可回放性 |
| SSE 契约 | `event_present` / `event_order` / `event_fields` | 事件存在性/顺序/字段完整性 |

### 7.3 场景组

黄金场景按能力组织，覆盖完整对话行为：标准对话（问候/讲解/搜题/诊断/周报/配平/导航/出题/审批/文件工具/身份场景）、LangGraph 专项（多工具链/审批流/中断恢复/护栏）、SSE 契约、工作流（空知识点必反问/生成后保存/搜索后反问/保存后导航/超限调用/跨角色）、内联面板（出题意图展示面板/显式搜索才搜索）、规划（复杂任务拆解/简单任务不拆解反例）、管理类动作（删除题库需审批/批量导入/分配练习）、端到端（诊断→计划/弱项→出题/六工具链/长对话）。

### 7.4 已知缺陷管理

已修复缺陷在回归维度统一登记（缺陷描述、发现/修复日期、涉及角色），防止复发；已知架构缺口（如搜索工具不读数据库、生成后不自动保存）单独登记并标注严重度与整改建议。

## 八、性能预算（L4）

### 8.1 指标采集

对任意 Agent 运行产出三项指标：**延迟**（墙钟耗时）、**token 消耗**（优先读模型响应上报的用量，读不到时记为"未测量"）、**循环数**（Agent 迭代轮次）。指标采集不侵入 Agent 本体（薄包装）。

### 8.2 软阈值（SLO）

| 指标 | 软警告阈值 | 说明 |
|------|-----------|------|
| 单轮延迟 p95 | ≤ 60 秒 | 与对话体验目标对齐 |
| 单次运行 token | ≤ 40k | 上下文预算上限 |
| 循环数 | ≤ 12 轮 | 与 Agent 递归上限对齐 |

SLO 以**软警告（warn）起步**：越界打印警告并计入报告，不进失败统计、不拦门禁；阈值先用真实数据校准，随慢跑层数据积累逐步收紧（转 fail 级另行决策）。循环数 SLO 与递归上限对齐，runaway loop 在切断前就能被指标发现。

## 九、报告与趋势

### 9.1 报告结构

每次运行输出结构化报告：

| 区块 | 内容 |
|------|------|
| 元信息 | 时间戳、评测组、触发来源 |
| 分层结果 | 每层每条目每个用例的状态（pass / pending / fail / severe / pass_expected） |
| 汇总 | 通过/失败/豁免/严重/告警计数 |
| 成本 | 判官调用次数、预估费用（¥） |
| 门禁结论 | verdict（通过/否决）+ 否决原因列表 |
| 耗时 | 总耗时 |

### 9.2 趋势与归档

- 每次运行按时间戳归档，历史序列持续累积——回答"Agent 变好还是变差"
- 慢跑层（有成本）强制归档；快跑层按需归档
- 未实现的层如实标注"未实现"，不填充空结果

### 9.3 落地基线

评估体系当前常驻规模：**pytest 313 项 + evals 快速轨 93 用例 + vitest 263 项**；47 个工具全链路验证（42 个领域工具 + 5 个浏览器工具，见 29 号设计文档）；判官五族中判卷族校准一致率 100% 已启用，其余四族以人机混合模式运行（校准数据持续积累）。

## 十、评测执行与验收

### 10.1 执行流程

```
1. 评测准备：搭建环境、准备黄金场景与校准集、配置判官密钥（独立于主链路）
2. 评测执行：
   ├── 快跑层（每次提交）：L0 工具断言 + L1 黄金场景 + L4 性能 SLO + L5 回归
   └── 慢跑层（夜间/发布前）：L2 判官五族 + L3 对抗语料 + L6 端到端
3. 评测分析：收集结果 → 对比门禁 → 生成报告（含成本与耗时）
4. 问题修复：记录未达标项 → 分析根因 → 修复后复测 → 通过后合入/发布
```

### 10.2 验收标准

- **快跑层**：100% 通过，无阻断级缺陷（任何确定性失败禁止合入）
- **慢跑层**：无 severe 级失败（化学错误/安全问题/端到端失败）；判官分数进入趋势但不拦发布
- **性能**：SLO 软警告可查，无失控循环
- **校准**：启用族一致率 ≥ 80%，未启用族走人机混合并持续补数据

## 十一、设计决策记录

**决策一：七层模型替代三分法。** 旧的"基线/边界/回归"三分法缺少判官层与工具自身正确性两层，无法评估答案质量，也无法度量"Agent 聪不聪明"。七层模型每层对应一个独立机制与节奏，层间不互相替代。

**决策二：慢跑层不用分数线门禁。** 判官分数有噪声，用分数拦发布会误伤。改为：**严重错误一票否决 + 分数只做趋势**。

**决策三：评估先行（eval-first）。** 先开发后评估 = "功能做完但没有可测目标"的模糊开发。评估即 spec：先写评估（红）→ 开发到绿 → 转常驻。

**决策四：判官与主模型解耦。** 判官用备选 provider，避免自评偏差；上线前实测判官能力，不足则人机混合兜底。

**决策五：校准门槛 80%（族粒度）。** 每族样本 ≥ 20 条、判官 vs 人工一致率 ≥ 80% 才启用自动计分；不达标走人机混合。启用决定在族粒度，不是全局开关。

**决策六：expected_fail 机制。** 红评估带标记不挡门禁（评估先行可落地），绿了提醒移除标记（不养死标记）。

## 附录：术语表

| 术语 | 说明 |
|------|------|
| 快跑层 / 慢跑层 | 按成本与耗时分的两层运行模式（快跑零 LLM 成本秒级；慢跑花 token 分钟级） |
| 判官（LLM-as-judge） | 用 LLM 按 rubric 给 Agent 输出/交互打分的评估机制 |
| rubric 库 | 按能力族组织的打分标准集合（五族） |
| 校准集 | 人工标注的样本集，用于验证判官与人工的一致性（门槛 ≥ 80%） |
| 黄金场景（golden scenario） | 输入 + 期望行为断言的评估用例 |
| 评估先行（eval-first） | 先写评估再开发的流程，评估即 spec |
