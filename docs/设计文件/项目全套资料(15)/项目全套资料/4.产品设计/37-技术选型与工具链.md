# 37. 技术选型与工具链 — ChemAI

> POC 验证了 AI 能做这件事。接下来的问题是：用什么做？怎么高效地做？技术选型决定了产品的能力边界、开发速度和长期维护成本。工具链决定了开发效率和代码质量底线。每个选择都对应着被放弃的替代方案和需要承担的后果。

---

## 一、选型方法论

三条原则：

1. **够用就好，不为未来过度设计**：选当前阶段需要的最简单方案，保留向上升级的路径
2. **优先选有社区验证的方案，避免"自研陷阱"**：自研只在现有方案确实满足不了需求时才考虑
3. **每个选择记录为 ADR（架构决策记录）**：不只记录"选了什么"，更记录"为什么选"和"放弃了什么"

## 二、LLM Provider 选型

### 2.1 选型方法：自研化学基准实测

不用公开 benchmark。设计了 **10 道覆盖高考化学六大板块的自测题**，逐个 Provider 实测评分：

| 题号 | 板块 | 知识点 | 来源 |
|:--:|------|--------|------|
| 1 | 离子反应 | 判断离子共存 | 2020 全国卷 T1 改编 |
| 2 | 氧化还原 | 配平 KMnO4 + HCl | 2020 全国卷 |
| 3 | 元素化合物 | Fe、Al 性质比较 | 2020 全国卷 T5 改编 |
| 4 | 化学反应速率 | 速率计算 | 2020 全国卷 T10 改编 |
| 5 | 化学平衡 | 勒夏特列原理判断 | 2020 全国卷 T10 改编 |
| 6 | 电化学 | 原电池/电解池判断 | 2020 全国卷 T6 改编 |
| 7 | 有机化学 | 官能团性质判断 | 2020 全国卷 T12 改编 |
| 8 | 物质结构 | 电子排布式书写 | 2020 全国卷 T11 改编 |
| 9 | 化学实验 | 气体制备装置选择 | 2021 湖南卷 |
| 10 | 计算 | 化学平衡常数计算 | 2020 全国卷 T10 改编 |

评分标准：2 分（全对）/ 1 分（细节遗漏）/ 0 分（关键错误）。

### 2.2 实测结果

| 维度 | DeepSeek（deepseek-chat） | MiMo-V2.5 | 通义千问 qwen-turbo |
|------|:--:|:--:|:--:|
| 化学准确率 | **20/20** | **20/20** | **18/20** |
| 失分原因 | — | — | 漏写反应条件、未说明尾气处理 |
| API 可用率 | 99.7% | 98.2% | 99.9% |
| 平均延迟 | 2.1s | 3.5s | 1.8s |
| P99 延迟 | 8.3s | 15.2s | 5.1s |
| 成本等级 | 最低 | 中等 | 低 |
| 视觉能力 | 不支持 | 支持 | 不支持（但提供 qwen-vl-ocr 专用模型） |
| 联网搜索 | 不支持 | 支持 | 不支持 |

### 2.3 决策：三级 Fallback 路由

首选 **通义千问 qwen-turbo**（最快延迟 1.8s、最高可用率 99.9%、复杂 JSON 生成稳定快速，同时提供 Embedding 与 qwen-vl-ocr 视觉模型） → 备选 **DeepSeek**（deepseek-chat，化学满分、成本最低） → 兜底 **MiMo-V2.5**（唯一原生支持视觉+联网搜索，用于需要检索/视觉的特定场景；复杂 JSON 生成偏慢且偶发返回空内容，故不担任主链路）。

Fallback 机制：每级 3 次重试 + 指数退避。

放弃海外模型（数据出境不合规、网络不稳定、成本高 20-50 倍）和自部署开源模型（种子阶段硬件投入 ROI 不匹配）。

### 2.4 成本评估

基于各 Provider 的公开定价和预期调用量，三 Provider 组合的月均 LLM 成本可控制在 ¥50-100 以内。通义千问作为主力模型承担大部分调用量，DeepSeek 承担批量生成与回退，MiMo 用于需要视觉/联网能力的场景。

## 三、Agent 框架选型

### 3.1 四轮迭代历程

| 迭代 | 框架 | 路由准确率 | 问题 |
|:--:|------|:--:|------|
| v0 | Pydantic AI | ~70% | 路由不稳定 |
| v1 | LangGraph Multi-Agent（Coordinator + Router + 6 Sub-Agent） | ~75% | 架构复杂、延迟高（2 次 LLM round-trip） |
| v2 | LangGraph 单 Agent（`create_react_agent` + Persona YAML 过滤） | **87%** | — |
| 保留 | LangGraph Multi-Agent（v1） | ~75% | 保留为 Fallback，通过 API 参数切换 |

### 3.2 决策：LangGraph `create_react_agent`（单 Agent）

让 LLM 从 42 个领域工具中自选，路由准确率 87%，高于 Coordinator+Router 的 75%。去掉 Coordinator 和 Router → 延迟降低 40%（P50 ~1.5s）。Checkpoint 持久化（AsyncSqliteStore）、SSE 流式输出（`astream_events`）开箱即用。

放弃 CrewAI/AutoGen（偏向 Agent 间对话，ChemAI 核心需求是工具调用准确率）、OpenAI Agents SDK（绑定 OpenAI，国内不可用）、Pydantic AI（实测路由准确率不够）、自研框架（种子期投入 2-3 个月 ROI 不匹配）。

## 四、前端选型

### 4.1 决策：React + Vite + Tailwind + antd + ECharts + KaTeX + Marked

| 依赖 | 版本 | 用途 |
|------|:--:|------|
| react / react-dom | ^19 | 教师端组件化 SPA |
| antd | ^6 | 基础组件库（表格、抽屉、弹窗、表单、消息） |
| echarts | ^6 | 学情图表渲染（KPI、趋势、分布、热力图） |
| vite | ^8.0.14 | 构建工具、HMR、API proxy（`/api` → `localhost:8000`） |
| tailwindcss | ^4 | 原子化 CSS，与 antd 组件协同 |
| katex | ^0.17.0 | 化学方程式 + 数学公式渲染 |
| marked | ^18.0.5 | Markdown 渲染（Agent 对话） |

学生端/家长端为移动优先的轻量页面，不引入框架构建步骤。

选择组件化 SPA 而非纯手写 DOM 的原因：Agent 对话的流式渲染（SSE 事件 → 消息组装 → 工具卡片/内联面板/审批卡片）、考试工作台多 Tab、学情图表等交互复杂度高，组件复用与状态管理的收益超过框架成本。化学式渲染采用 KaTeX + mhchem——唯一能正确渲染化学方程式的开源方案。

桌面端 **pywebview** + 内嵌 Uvicorn 服务器（127.0.0.1:8000），PyInstaller 6.x 打包为 .exe。

## 五、数据库选型

### 5.1 决策：SQLite + WAL（开发），MySQL 可选（生产）

SQLite 配置要点：启用 WAL 模式（支持读写并发）、NORMAL 同步模式（平衡安全与性能）、外键约束、8MB 缓存、5 秒锁等待超时。

零运维成本、Docker 单容器部署。SQLAlchemy ORM 抽象，切换到 MySQL 改一行连接字符串即可。

三个数据库文件：`主数据库`（主库）、`Agent检查点数据库`（Agent 状态）、`Agent长期记忆数据库`（长期记忆）。

向量检索 **ChromaDB 0.4.22**（嵌入式、零运维、metadata 过滤），Embedding 模型为 DashScope text-embedding-v3（1024 维）。

放弃 PostgreSQL 的原因：单校部署场景下运维成本远超实际需求。

## 六、OCR 管道选型

| 方案 | 定位 | 说明 |
|------|------|------|
| PP-OCRv6（paddle） | 答题卡默认引擎 | 本地开源、免费、onnxruntime 推理无网络依赖，针对答题卡手写场景优化 |
| 百度 AI 教育 OCR | 在线高精度降级 | doc_analysis（预览+公式提取）、paper_cut_edu_vlm（切题识别异步批量）、correct_edu（批改识别，3s 轮询 120s 超时） |
| Qwen-VL-OCR | 补充VLM选项 | 百炼 qwen-vl-ocr 模型，图片直转 Markdown，作为 GLM-4V/MiMo 之外的补充视觉方案 |
| MinerU | PDF 解析 | 独立管线，试卷 PDF → MD/JSON 结构化，LaTeX 公式标准化 |

三引擎降级链设计详见 [23-答题卡OCR批改系统设计](./23-答题卡OCR批改系统设计.md)。核心路由策略：
- 答题卡图片 → PP-OCRv6 默认 → 失败降级百度 OCR → 最终降级 VLM（GLM-4V / MiMo）
- PDF 文件 → MinerU 优先 → 失败降级百度 OCR → 最终降级 VLM（GLM-4V / MiMo）
- 图片文件 → 百度 OCR 优先 → 失败降级 MinerU → 最终降级 VLM（GLM-4V / MiMo）
- 混合文档 → MinerU + 百度 OCR 并行 → 合并结果 → 失败降级 VLM

## 八、开发工具链

ChemAI 的开发工具链分为五层，定义于 `5.AI Coding工程实践/AI coding自然语言版/00-总体开发方案.md`：

```
思考层：  /office-hours  /plan-ceo-review  /plan-eng-review  ← 开发流程工具集
规格层：  /opsx:propose  →  /opsx:apply  →  /opsx:archive  ← 规格驱动开发框架
实现层：  写测试(RED)  →  Claude生成(GREEN)  →  重构     ← TDD
质量层：  L1单元  →  L2集成  →  L3 Golden  →  基线对比    ← Evals
流程层：  /review  /cso  /qa  /ship  /retro  /investigate  ← 开发流程工具集
骨架层：  branch  commit  tag  merge  revert  push      ← Git
```

| 工具 | 在流程中的角色 |
|------|--------------|
| **AI 编程助手** | 执行规格任务、生成代码、操作 Git |
| **规格驱动开发框架** | 创建变更提案 → 读取规格生成代码 → 归档 |
| **开发流程工具集** | 50+ 个角色命令覆盖全流程——思考层（战略讨论/架构审查）和流程层（代码审查/安全审计/QA测试/发布/复盘），将 AI 编程助手 变成一个"虚拟工程团队" |
| **TDD** | 用户写测试（RED） → Claude 生成实现（GREEN） → pytest 验证，内嵌在 `/opsx:apply` 循环中 |
| **Evals** | Golden 数据集 + L0-L6 分层评测（fast/slow 双轨）+ 14 维度门禁（warning/critical 双阈值）+ severe 一票否决 + 回归基线对比 |
| **Git** | 骨架层：分支隔离 → 原子化 commit → tag 标记质量节点 → 回退修复 |
