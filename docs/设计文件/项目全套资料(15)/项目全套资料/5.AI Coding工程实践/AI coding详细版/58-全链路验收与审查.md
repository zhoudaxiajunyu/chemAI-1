## 一、本阶段目标

| 维度 | 内容 |
|------|------|
| **产出** | 验收报告 + 14页面全量QA通过 + Evals基线对比无劣化 |
| **Git分支** | `phase-7/ship`（从main切出） |
| **使用工具** | `/qa-only` `/design-review` `run_evals` `/investigate` |
| **质量门禁** | 14页面无致命缺陷 + 视觉一致性通过 + Evals劣化不超5% |

验收是阶段七的前半部分——用Gstack自动化工具对所有页面、API、Evals做最后一轮检查，修复发现的问题，打出 `v1.0.0-rc.1` 标签。

**为什么用自动化工具而不是手动验证？** 前六个阶段（文档42-57）我们通过 `/opsx:apply` + TDD 逐模块保证质量。验收阶段需要的是"广度检查"——覆盖全部14个页面和所有API端点，而非深度审查单个模块。Gstack 的 `/qa-only` 用自动化遍历代替手动逐页检查——速度快且不会遗漏。

### Step 2: 自动化QA — 14页面全量

**操作**（在Claude Code中输入）：

```
/qa-only
```

`/qa-only` 是Gstack的纯自动化QA命令，区别于 `/qa`（交互式）。它会：

1. 逐一打开14个页面URL（`http://localhost:8000/teacher/chat` 等）
2. 检测：页面加载时间、控制台JS错误、UI元素缺失、按钮不可用、表单无法提交
3. 对可自动交互的元素执行点击/输入操作
4. 输出每页的交互通过率（目标 >= 90%）
5. 生成结构化QA报告，标注每个失败项的位置和截图

**手动补充验证**（`/qa-only` 无法自动判断的交互，需手动确认，每个约1-2分钟）：

| 页面 | 手动验证点 | 为什么自动化不行 |
|------|-----------|----------------|
| Agent对话页 | SSE流式输出是否逐字显示、工具调用状态提示是否出现 | 流式内容的时序判断需要人眼确认 |
| 出题工作台 | `\ce{H2SO4}` 等化学公式是否渲染为可视化分子式而非LaTeX源码 | 公式渲染的正确性需要化学知识判断 |
| 学情面板 | ECharts图表是否正常渲染（canvas不为空白）、3D散点图是否可拖拽旋转 | 图表内容正确性需要人工比对数据 |
| OCR批改 | 上传手写答题卡 → 确认识别结果 + 自动评分的全链路 | 手写识别准确率需要人眼比对 |
| 学生练习页 | 提交答案后的即时反馈是否正确（正确显示绿色、错误显示红色+解析） | 反馈内容需要学科知识判断 |
| 错题本 | 错题解析中的化学公式是否正确渲染 | 同上 |

**记录所有问题**到 `acceptance-checklist.md`，每条标注来源（`/qa-only` 或手动）和严重程度。

**`/qa-only` 报告你应重点关注**：
- 通过率 < 90% 的页面：必须修复后重新运行
- `Console errors > 0` 的页面：点开Console看具体错误，JS异常必须清零
- `Load time > 5s` 的页面：检查是否有阻塞的网络请求

**如果出错**：

| 错误 | 原因 | 解决 |
|------|------|------|
| `/qa-only` 命令不可用 | Gstack 技能包未安装 | 回到文档42 Step 4 安装 Gstack；或用手动浏览器打开14个页面的 URL 逐页验证替代 |
| 页面加载超时（多个页面 > 10s 无响应） | 后端 API 未启动或 8000 端口未监听 | `curl http://localhost:8000/health` 确认后端存活；若未启动则 `uvicorn app.main:app --port 8000` ；检查 SQLite 数据库文件 `chemai.db` 是否存在 |
| 交互通过率低于 90% | 前端组件存在未处理的 JavaScript 异常或 API 调用失败 | 打开浏览器 DevTools Console 逐页检查红色报错；优先修复导致按钮/表单不可用的 JS 错误；修复后重新运行 `/qa-only` |
| 控制台有 JavaScript 错误 | 前端构建产物与后端 API 版本不匹配、或静态资源 404 | 重新构建前端 `npm run build`；确认 `frontend/dist/assets/` 下所有 JS/CSS 文件可访问 |
| SSE 流式输出验证失败 | Agent 对话页的 EventSource 连接中断或后端未正确发送 `text/event-stream` | 检查后端 `/api/agent/chat` 端点是否返回 `Content-Type: text/event-stream`；确认前端 `EventSource` 未因 CORS 被拦截 |

### Step 3: 视觉审查 + API全量测试

**视觉审查**（在Claude Code中输入）：


Gstack `design-review` 命令对照文档41的14个原型，检查：

**API全量测试**（在Claude Code中输入）：

```
请帮我运行API全量测试：扫描 backend/app/routers/ 下的所有路由，对每个端点自动生成测试用例（正常200 / 未认证401 / 无效参数422 / 不存在资源404），然后全部运行，生成HTML格式报告保存到 reports/api-test-report.html。
```

**API测试通过标准**：
- 通过率 >= 95%（少量端点可能因种子数据缺失而404，记录即可）
- 所有"未认证返回401"测试必须100%通过
- 如有失败，定位原因并记录到验收清单

**如果出错**：

| 错误 | 原因 | 解决 |
|------|------|------|
| `/design-review` 报告大量不一致（颜色、布局、间距均有差异） | 原型文件（文档41的 HTML 原型）缺失，或 DESIGN.md 中色值定义与实际 CSS 不一致 | 回到文档41确认原型可访问；检查 DESIGN.md 中色值/间距定义与前端 CSS 是否一致；用浏览器 DevTools 取色器逐一比对 |
| API 端点返回 401 未认证 | JWT token 已过期或 Authorization header 格式错误 | 重新登录获取新 token；确认请求头格式为 `Authorization: Bearer <token>`；检查 token 是否在生成后超过 7200 秒 |
| API 端点返回 422 参数校验失败 | 请求体字段名与 Pydantic schema 不匹配、或字段类型错误 | 打开 `http://localhost:8000/docs` 查看 Swagger 中对应端点的 Request Body schema；对照修正测试脚本中的字段名和类型 |
| API 测试脚本未找到路由文件 | `backend/app/routers/` 目录结构变化或路由文件命名不规范 | `ls backend/app/routers/` 确认路由文件存在；检查 `app/main.py` 中 `app.include_router()` 是否已注册所有路由模块 |

### Step 4: Evals最终基线对比

这是验收阶段最关键的质量门禁——确认前六个阶段的所有修改没有导致整体质量退化。

**操作**（在终端或Claude Code中输入）：

```bash
run_evals --tier all --compare baseline.json
```

**三层评测全部运行**：

| 层级 | 内容 | 通过标准 |
|------|------|:------:|
| L1 单元 | 纯函数逻辑（规则引擎、置信度、状态机） | >= 95% |
| L2 集成 | API端点行为（结构、状态码、认证） | >= 90% |
| L3 质量 | AI内容质量（科学性、诊断准确率、辅导安全性） | >= 70% |

**决策树**：

```
run_evals --compare baseline.json
  │
  ├── 无劣化 或 劣化 ≤ 3%
  │   正常波动，记录到验收报告，继续。
  │
  ├── 劣化 3-5%
  │   需要处理：
  │   /investigate → 定位失败的Evals样本（如 golden_031、golden_077）
  │   → 修复代码 → git commit -m "fix(golden-NNN): [问题描述]"
  │   → 重新 run_evals --tier all --compare baseline.json
  │
  └── 劣化 > 5%
      严重退化，优先回退：
      /investigate → 定位bad commit
      → git revert <bad-commit>
      → 重新 run_evals
      或选择方案B：直接修复 → git commit → 重新 run_evals
```

**决策原则**：
- 3%以下：直接过，不做无意义的微调（过度优化可能导致过拟合）
- 3-5%：定位到具体样本修复，不能"改阈值凑数"
- 5%以上：revert优先——大范围劣化通常意味着某个commit有问题，逐个revert比逐个修快

**打标签**（在Claude Code中输入）：

| 修复 A 导致 B 回归（修复一个 bug 后其他页面的 `/qa-only` 通过率下降） | 修改的代码被多个页面共享（如公共组件、API 工具函数） | 修复前运行全量 `/qa-only` 记录基线通过率；修复后重新运行全量 `/qa-only` 对比；若出现回归，检查修改的文件是否被多个路由/组件引用 |
| 某个严重问题长时间无法修复 | 根因涉及底层架构（如数据库迁移冲突、认证流程改造） | 评估是否可以降级处理（如临时禁用该功能并记录为"已知问题"）；若为阻断性严重问题（如页面白屏），则暂停验收、回到对应阶段文档重新开发 |
| `git revert` 后 Evals 仍未恢复（劣化仍然 > 5%） | revert 了错误的 commit，或劣化由多个 commit 累积造成 | `git log --oneline --all --graph` 可视化分支历史；逐个 revert 怀疑的 commit 并每次运行 `run_evals` 验证；必要时 `git bisect` 二分定位 |
| 验收签字清单中"发布建议"为"不能发布" | 存在未解决的严重或高级别问题 | 回到 Step 5 修复循环，逐项处理严重/高问题；全部清零后重新生成验收签字清单；确认三个条件全部满足：严重=0、高=0、Evals 劣化 <= 5% |
