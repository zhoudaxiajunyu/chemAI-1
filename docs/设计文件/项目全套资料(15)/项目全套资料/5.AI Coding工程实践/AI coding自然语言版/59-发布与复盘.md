## 三、开发流程

### Step 0: `/no-mistakes`（发布前最终确认）

在开始正式发布流程之前，做最后一次门禁确认。

> **注意**：no-mistakes 不是"发布时才用"的工具——从文档 43 起，**每次 push 都已经在过它的闸**（`git push no-mistakes` 自动跑 review → test → docs → lint 流水线）。这里的 Step 0 是发布前的**最后一次全流水线确认**，确保从上次 push 到现在的改动也干净。

**操作**（在Claude Code中输入）：

```
/no-mistakes
```

`/no-mistakes` 是 **no-mistakes 门禁工具**（独立于 Gstack，文档 42 已安装）的 Agent 技能。它触发完整流水线：**review → test → docs → lint → push → PR → CI**，任何一步不绿就停在原地等你处理。

跑完流水线后，对照下面的**发布前检查清单**逐项确认（这些是 no-mistakes 不自动覆盖的人工确认项）：

1. **Git状态验证**：确认工作区干净、当前在 `phase-7/ship` 分支、无未提交变更
2. **测试最终确认**：重新运行核心测试套件，确认全部通过
3. **Evals最终快照**：运行 `run_evals --tier all --compare baseline.json` 最后一次，确认无劣化
4. **安全检查**：确认 `.env` 未在 Git 跟踪中、无硬编码密钥、依赖无已知高危CVE
5. **部署就绪检查**：确认 Dockerfile 和 docker-compose.yml 存在且配置正确
6. **回滚预案确认**：确认上一个稳定版本 tag 可访问、回滚脚本存在

**如果门禁不通过**：
- 任何一项检查不通过都会阻断发布
- 根据提示逐一修复后重新运行 `/no-mistakes`
- 全部通过后才允许进入 Step 1

**这个步骤不能跳过**——它是上线前的最后一道安全网，确保没有低级错误被带到生产环境。

### Step 1: `/ship`（合并 + 测试 + changelog + PR）

**操作**（在Claude Code中输入）：

```
/ship
```

`/ship` 自动执行以下6步流程，每步都有进度提示：

| 步骤 | 操作 | 说明 |
|:--:|------|------|
| 1 | Merge `phase-7/ship` -> `main` | `git merge --no-ff` 保留Phase 7完整历史 |
| 2 | Run full test suite | pytest（后端测试），前端为浏览器手动验证 |
| 3 | Bump version | `v1.0.0-rc.1` -> `v1.0.0` |
| 4 | Generate CHANGELOG | 从 `git log` 按 Conventional Commits 分组（feat/fix/test/docs/chore） |
| 5 | Tag v1.0.0 | `git tag -a v1.0.0 -m "ChemAI v1.0.0 正式发布"` |
| 6 | Push + 开 PR | 推送分支并创建 PR（人类审查后手动 merge，Agent 永不自动合并） |

**你应该看到**：

```
🚀 Ship started at [timestamp]

[1/6] Merging phase-7/ship to main (--no-ff)... ✅
[2/6] Running full test suite (pytest)... ✅  [498 passed, 0 failed]
[3/6] Bumping version... v1.0.0-rc.1 -> v1.0.0  ✅
[4/6] Generating CHANGELOG.md... ✅
[5/6] Tagging v1.0.0... ✅
[6/6] Building Docker images... ✅

Ship complete. v1.0.0 is ready for deployment.
Next: run /land-and-deploy to start canary rollout.
```

**如果 `/ship` 中途失败**：

| 失败步骤 | 常见原因 | 处理方式 |
|---------|---------|---------|
| Merge冲突 | 有其他commit进入了main | 解决冲突后重新merge |
| 测试失败 | rc.1打tag后有未测试的修改 | 修复 -> 测试 -> 重新commit到phase-7/ship -> 重新/ship |
| Docker build失败 | Dockerfile基础镜像拉取失败 | 检查网络/镜像仓库权限 |
| Tag冲突 | v1.0.0 tag已存在 | `git tag -d v1.0.0` 删除旧的，重新/ship |

**验证**：
- `git tag | grep v1.0.0` 确认tag存在
- `cat CHANGELOG.md` 确认内容完整，按类型分组，链接到对应的commit

### Step 2: `/land-and-deploy`（部署 + 生产验证）

**操作**（在Claude Code中输入）：

```
/land-and-deploy
```

`/land-and-deploy` 负责：**合并PR → 等待部署完成 → 生产健康验证（canary检查）**。它会自动识别部署平台（Vercel/Netlify/Docker等），部署完成后对生产地址做一轮健康检查，全部通过才算落地成功。

**灰度扩量（如果部署平台支持）**：灰度发布的百分比控制由部署平台完成（如K8s按比例路由、负载均衡权重），`/land-and-deploy` 负责每阶段部署后的验证。推荐节奏：

```
灰度 5%  ──观察2h──>  灰度 25%  ──观察1h──>  灰度 50%  ──观察1h──>  灰度 100%
  │                      │                      │                      │
  ├── 错误率 < 1%        ├── 错误率 < 1%        ├── 错误率 < 1%        └── 全量发布
  ├── p95 < 500ms       ├── 重点看DB连接池     ├── DB连接池 < 80%
  └── Agent成功率>95%    └── 用户反馈正常       └── 稳定无告警
```

**每阶段观察的关键指标**：

| 指标 | 正常值 | 告警阈值 | 说明 |
|------|:------:|:------:|------|
| API错误率 | < 0.5% | > 5%触发P0，> 1%触发P1 | 500错误占比所有请求 |
| API p95延迟（非LLM） | < 300ms | > 3s触发P1 | 不含Agent对话等LLM调用 |
| Agent对话成功率 | > 95% | < 90%触发P1 | 返回有意义回复的比例 |
| 数据库连接池使用率 | < 60% | > 90%触发P1 | 接近上限需扩容 |
| Redis内存使用率 | < 60% | > 80%触发P2 | 接近上限需扩容 |

**灰度通过准则**：
- 5%阶段：观察时间最长——这是最关键的观测窗口，大部分问题在这一阶段暴露
- 25% -> 50%阶段：确认高负载下稳定性后推进
- 任一阶段出现P0告警：立即终止，回滚到上一阶段，定位问题后重新开始

### Step 3: `/canary`（金丝雀监控）

**操作**（在Claude Code中输入）：

```
/canary <生产URL>
```

`/canary` 是部署后的**持续监控循环**（Gstack技能）：在指定时间段内周期性检查生产环境，包括：

1. **浏览器级健康检查**：页面是否能打开、控制台有无报错、关键交互是否正常
2. **性能回归检测**：页面加载时间、资源体积是否异常（对比 `/benchmark` 基线）
3. **自动发现异常**：监控期间发现新问题会自动记录并提示
4. **回滚决策支持**：出现严重异常时，提供回滚建议（`/land-and-deploy` 也支持回滚）

**`/canary` 的使用时机**：
- `/land-and-deploy` 完成部署验证后，对生产环境做持续观察（建议10分钟）
- 灰度扩量期间，每个阶段推进前跑一轮
- 收到监控告警后，定位和决策时

**推进到下一阶段**：灰度阶段推进由你根据 `/canary` 的监控结果决定——确认无异常后，在部署平台把流量比例调高，然后再次运行 `/canary` 验证新阶段。

### Step 4: `/retro`（工程回顾）

**操作**（在Claude Code中输入）：

```
/retro
```

`/retro` 引导结构化复盘，最终产出 `retros/v1.0-retro.md`，包含四部分：

**Part 1 — 数据事实（What happened?）**：

从首日数据中提取关键指标：
- 用户数据：注册教师数、注册学生数、注册家长数、DAU
- 使用数据：Agent对话总数、题目生成数（含审核通过数）、学生练习完成数、OCR批改次数、障碍诊断次数
- 质量数据：题目四维审核通过率、L3 Evals对比baseline的通过率趋势、Golden回归清单状态
- 系统数据：总请求数、错误率、API p50/p95/p99、CPU/内存峰值
- 对比项目目标（当初设定的成功标准），标注偏差

**Part 2 — 哪些做得好（What went well?）**：

每个人通常从以下角度各列至少2条，每条用具体数据或事例支撑：
- 流程角度：哪些实践提升了效率（如TDD下regression bug发现时间从2h -> 15min）
- 技术角度：哪些技术决策证明是正确的（如ChromaDB 向量检索 vs 专用向量数据库的成本节省）
- 协作角度：AI Coding哪个环节最顺畅（如规格先行减少了多少返工）

**Part 3 — 哪些可以改进（What can be improved?）**：

同样各列至少2条，每条附具体改进建议：
- 流程角度：哪些环节卡顿、浪费时间（如Evals全量跑一次太慢 -> 引入增量Evals）
- 技术角度：哪些选型需要重新评估（如SSE vs WebSocket的性能差异在100+并发下暴露）
- 产品角度：用户反馈中暴露的问题（如教师反映四维审核太严格导致大部分题目不通过）

**Part 4 — 下一步行动计划（Action items）**：

按时间维度规划：
- 短期（本周）：3个最高优先级的修复/改进 -> 在 `release/v1.0` 分支上以hotfix形式发布 `v1.0.1`
- 中期（本月）：3个功能迭代方向 -> `phase-1/v1.1` 新分支
- 长期（下季度）：3个战略方向 -> 如多学科扩展、学校LMS对接

**复盘质量标准**：
- 每条"做得好"和"需改进"都有具体数据或事例——不接受"代码质量好"这种泛泛之谈
- "需改进"的每条都必须有可执行的改进建议——不是"下次注意"而是"下次用X工具做Y检查"
- "行动计划"中的每项都有预估时间——避免一切"下季度做"的拖延
