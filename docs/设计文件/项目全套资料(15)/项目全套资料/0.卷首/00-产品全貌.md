## 一、产品定义

ChemAI 是一套面向高中化学教学的 AI Agent 系统。它不是一个搜题工具，不是一个题库软件，不是一个通用 AI 聊天套壳——而是一个能理解化学学科深层逻辑的 AI 教研助手。rag/单agent（langraph）、微调（embed

**核心能力**：帮助老师出题、批改、诊断学生的真正学习障碍；帮助学生在 AI 的引导下自己推导出答案；帮助家长看懂孩子的学习状态。

**产品形态**：Web 应用，包含教师端（考试工作台 + 诊断面板 + 答题卡 OCR 批改）、学生端（AI 助教对话 + 练习 + 错题本）、家长端（学情周报）。

**技术架构**：LangGraph 驱动的 Agent 系统 → 22 个专业化学工具 → Persona 多角色隔离 → AsyncSqliteSaver 记忆管理 → 14 维度评测体系 → FastAPI （py）+ SQLite（PG、mysql） + Docker 部署。

## 二、为什么要做这个产品

### 2.1 市场缺口

2026 年中国有约 30 万高中化学教师、约 580-600 万化学选考生（教育部 2025 年统计：58.7% 高考生选择"物理+化学"组合）。市面上有科大讯飞的阅卷系统（能告诉你"全班正确率 65%"），有作业帮的搜题工具（能告诉你"这道题的答案是什么"），有学科网的题库（能让你下载试卷，约¥9,000-30,000/年）。

**但没有人回答"这个学生为什么错"。**

- "这道题全班 35% 的人错了"——这是统计
- "这 35% 的人里，有的是概念模糊，有的是审题失误，有的是表述能力不足"——这是诊断
- 统计现有产品都能做，诊断只有 ChemAI 在做

### 2.2 教师痛点量化

一位高中化学老师每次考试后的错因分析耗时 6-10 小时——这 6-10 小时是"纯体力统计"：翻试卷、分类错题、手写统计、做 Excel。真正需要专业能力的"个性化讲评和辅导"反而没时间做。

这不是个案。《中国教育学刊》2023 年对全国 48,874 名教师的大样本调研显示：68.3% 的教师日工作时长超过 8 小时，37.5% 的教师每天批改作业超过 80 份，86.25% 的教师承受轻度以上工作压力。化学学科因方程式配平、离子方程式拆分、有机推断等需要逐步骤判断，批改一张化学试卷的时间至少是数学的 1.5 倍。

ChemAI 把这个流程压到 45 分钟——87.5% 的时间节省——让老师把精力花在"怎么教"而不是"统计错题"上。

### 2.3 政策窗口

2021 年"双减"政策压缩了校外培训，但学习质量提升的需求从"校外"转移到了"校内"。2023-2025 年教育部密集出台的政策——从《基础教育课程教学改革深化行动方案》（2023）到教育部等九部门《关于加快推进教育数字化的意见》（2025.04）再到教育部基础教育教学指导委员会《中小学生成式人工智能使用指南（2025年版）》（2025.05）——反复强调同一个方向：用数字化手段赋能校内教学质量提升，利用 AI 辅助教学分析和学生诊断。该指南明确了学段差异化管理：高中阶段允许结合技术原理开展探究性学习，同时要求建立"白名单"制度、算法备案、数据本地化和内容审核机制。ChemAI 的产品定位与这些政策高度一致。

## 四、Agent 系统详解

这是 ChemAI 最核心的子系统。Agent 层的设计质量直接决定了"AI 助教"是真正有用还是只是一个套壳聊天。

### 4.1 Agent编排架构（v2）

ChemAI 采用 **单 Agent + 工具集 + Persona 过滤** 架构（LangGraph `create_react_agent`）。

**执行流程**：

```
用户输入（"帮我配平 Fe + O2 = Fe2O3"）
  │
  ▼
Gateway 意图分类（chat 还是 navigate？）
  │
  ▼
Persona 注入（你是谁？你能用什么工具？你的行为边界是什么？）
  │
  ▼
GuardState 初始化（去重记录、调用计数、审批状态）
  │
  ▼
ReAct 循环（最多 12 轮）：
  ┌──────────────────────────────────────┐
  │ Thought: "用户要配平，应该用            │
  │           balance_equation 工具"       │
  │    ↓                                  │
  │ Action: 调用 balance_equation          │
  │    ↓                                  │
  │ Observation: 工具返回配平结果           │
  │    ↓                                  │
  │ Thought: "配平完成，总结结果告诉用户"    │
  └──────────────────────────────────────┘
  │
  ▼
SSE 流式输出（token-level streaming）
```

**为什么 v2 选择了单 Agent 而非多 Agent？**

v1 使用的是 Coordinator + Router + 6 个 Sub-Agent 的多 Agent 架构。Coordinator 负责将请求路由到正确的 Sub-Agent（出题专家/诊断专家/辅导专家等）。

问题：Coordinator 的路由准确率约 70-75%。"离子方程式"请求经常被错误路由到"出题专家"而非"化学辅导"。而且每条请求经过 Coordinator（1 次 LLM 调用）+ Router（1 次 LLM 调用）= 至少 2 次 round-trip。

v2 让 LLM 自己从 22 个工具中选择——路由准确率提升到 85%+，延迟降半。

### 4.2 Persona 系统（角色隔离）

ChemAI 的 4 个角色不是"同一套 Prompt 换了个名字"——它们的工具集和 system_prompt 完全独立。

```
student（学生版 AI 助教）
  工具：chemistry_tutor, simulate_experiment,
        ionic_equation_tutor, stoichiometry_tutor,
        redox_tutor, equilibrium_tutor
  策略：引导式教学，不给答案，苏格拉底式提问
  禁止：balance_equation（直接配平=给答案）、
        show_exam_workbench（这是教师工具）

teacher（教研助手）
  工具：show_exam_workbench, diagnose_barrier,
        search_exam_bank, balance_equation,
        assign_adaptive_practice, show_students
  策略：高效批改+诊断+出题

tutor（通用化学助教，开发/演示用）
  工具：chemistry_tutor, balance_equation,
        search_exam_bank, web_search

parent（家长助手）
  工具：weekly_report, diagnose_barrier
  策略：通俗语言，不展示排名（家长看不到学生的考试排名）
```

**实现方式**：每个角色一个 YAML 文件（`agent/personas/{role}.yaml`），定义 `system_prompt` + `available_skills`。工具在 `TOOL_META` 中声明自己属于哪些角色。Agent 创建时自动取交集过滤。

**Persona 隔离不止是代码逻辑——它有评测保证。** `test_student_cannot_access_teacher_tools` 评测断言：student persona 的工具集里不能有 `show_exam_workbench`、`balance_equation` 等教师工具。如果开发者不小心加错了，CI 在 5 秒内阻断。

### 4.3 工具系统（22 个专业化学工具）

工具不是"让 LLM 自由发挥"的出口——它们是**行为约束**。每个工具通过 `docstring` 告诉 Agent：什么时候该用我、我会做什么、下一步要做什么、什么场景不要用我。

```
搜索类                          辅导类（工厂模式）
  search_exam_bank                 chemistry_tutor
  web_search                       ionic_equation_tutor
                                   stoichiometry_tutor
出题类                             redox_tutor
  generate_questions               equilibrium_tutor
  show_exam_workbench              periodic_law_tutor
  save_to_bank                     organic_tutor

诊断类                            记忆类
  diagnose_barrier                 memory_student_get
  show_diagnosis                   memory_teacher_get

化学工具                          导航/审批类
  balance_equation                 show_students
  simulate_experiment              browse_navigate/browse_read/...
                                   request_approval
OCR 类
  query_ocr_progress              练习类
  grade_answer_sheets              assign_adaptive_practice
  save_grading_results             weekly_report  
```

**Tutoring tool 工厂模式**：7 个化学辅导工具共享完全相同的三分支结构（有输入→给反馈 / 学生回复→给引导 / 无输入→给介绍）。通过 `_make_tutor_tool` 工厂函数，每个新 tutoring tool 只需 15 行配置。改引导逻辑 = 改工厂一处 → 7 个工具全部受益。

### 4.4 记忆管理（三层架构）

ChemAI 的记忆系统不只是"记住对话"——它是一个三层记忆架构：

```
┌─────────────────────────────────────┐
│  工作记忆（Working Memory）          │
│  滑动窗口：最近 20 轮对话             │
│  实现：AsyncSqliteSaver checkpoint   │
│  保证：跨请求、跨页面、服务重启不丢失  │
├─────────────────────────────────────┤
│  情景记忆（Episodic Memory）         │
│  关键事件：学生卡在某个知识点          │
│          学生表现出某个障碍类型        │
│          教师的诊断修正记录            │
│  实现：MemoryStack（agent/memory.py） │
├─────────────────────────────────────┤
│  学生画像（Student Profile）         │
│  长期特征：知识掌握热力图              │
│           常见障碍类型分布             │
│           进步趋势                    │
│  实现：SQLite Student 表 +             │
│        LangGraph AsyncSqliteStore     │
└─────────────────────────────────────┘
```

**对话持久化（AsyncSqliteSaver）**：v2 使用 SQLite 持久化 Agent 对话状态。为什么不用内存？因为 HTTP 是无状态的——第一个请求创建的 Agent A 写入状态到 A 的 saver，第二个请求创建的 Agent B 有自己独立的 saver，读不到 A 的状态 → 学生发现"AI 不记得刚才说了什么"。AsyncSqliteSaver 全局单例解决了这个问题。

**上下文裁剪（Context Trim）**：对话长了怎么办？三层混合策略：无条件保留最后 6 条 + 有条件保留含关键字的（"配平""不会""步骤"等）+ LLM 摘要压缩超过 30 条的历史。结果：context 控制在 15-20 条消息等效范围内，P95 延迟 < 3s。

### 4.5 SSE 流式输出

Agent 的回复通过 Server-Sent Events（SSE）逐 token 流式输出到前端——学生看到 AI 在"打字"，而不是等 3 秒后弹出一大段。

**去重机制**：ReAct 循环中，工具返回了 "配平结果: 4Fe + 3O2 = 2Fe2O3"，LLM 紧接着又说一遍——学生会看到两遍同样的内容。SSE dedup 在工具层和文本层都做了去重。

### 4.6 GuardState（护栏层）

每次工具调用前经过护栏检查：

| 护栏 | 作用 | 示例 |
|------|------|------|
| **去重** | 防止 LLM 对同一输入重复调用同一工具 | `seen_calls` 记录已调用的 (tool, input) 对 |
| **调用限制** | 防止 LLM 陷入无限循环 | `balance_equation` 最多 5 次/请求 |
| **审批门控** | 破坏性操作需用户确认 | `assign_adaptive_practice` 必须先调 `request_approval` |
| **递归限制** | 防止 ReAct 循环爆炸 | 最多 12 轮迭代 |
| **_route 剥离** | 防止内部路由信息泄露 | `_route` 字段在传给 LLM 前剥离 |

## 五、评测体系

Agent 的行为不是确定性的——同一个 Prompt 两次调用可能不同。所以不能靠"测一下看对不对"，必须靠系统化的评测。

### 5.1 两层架构

```
确定性评测（86 个，< 5 秒）        API 评测（36 个，~2 分钟）
不调 LLM，纯代码断言                真正运行 Agent
─────────────────────              ─────────────────
Persona 隔离验证                   路由准确性（32 场景）
危险品过滤验证                     工具调用准确性（8 场景）
checkpoint 读写验证                工作流完整性（12 场景）
配置一致性验证                     边界情况（12 场景）
性能基线测量                       计划连贯性（4 场景）
已知 bug 回归
```

### 5.2 CI 门禁

```
确定性评测 86 个
  ├─ 安全层失败 → ❌ CI 阻断（不可绕过）
  ├─ 回归层失败 → ❌ CI 阻断（不可绕过）
  └─ 全部通过 → 继续

API 评测 36 个
  ├─ 路由准确性 ≥ 85% → ✅ 通过
  ├─ 路由准确性 75-85% → ⚠️ 告警但放行
  └─ 路由准确性 < 75% → ❌ CI 阻断
```

**为什么安全层要求 100% 而路由层只要求 85%？** 学生看到教师工具是不可接受的底线——没有"概率"的容错空间。而 LLM 的非确定性意味着路由不可能每次完美——85% 是经验上"基本可靠"的线。

### 5.3 评测覆盖诚实原则

如果一个维度的所有场景在当前测试集下都没有被触发，该维度报告为 `null`，不是 `100%`。`0/0` 不是 `100%`——它意味着"我们不知道这一层有没有问题"。

> 深度阅读：`第五部分-工程实现/23-评测体系.md`（14 维度详解、阈值设计原理、评测驱动的产品决策案例）

## 六、数据架构

### 6.1 数据库设计

ChemAI 使用 SQLite + WAL 模式，12 张核心业务表通过 SQLAlchemy ORM 管理：

| 表 | 用途 | 关键字段 |
|----|------|---------|
| `teachers` | 教师账户 | school_id, subject |
| `students` | 学生档案 | class_id, barrier_profile（障碍画像）|
| `classes` | 班级 | teacher_id, grade |
| `schools` | 学校 | name, region |
| `exam_records` | 考试/练习记录 | class_id, type, status |
| `questions` | 题库 | content, answer, knowledge_point, difficulty, source（AI/手动/OCR） |
| `student_answers` | 学生作答 | exam_id, question_id, answer, is_correct |
| `barrier_configs` | 障碍诊断配置 | barrier_type, rules |
| `accounts` | 登录凭证 | bcrypt hashed password, JWT |

### 6.2 数据闭环

ChemAI 不是"AI 猜一下这个学生有什么问题"，而是基于**这个学生真实的每道题作答记录**：

```
老师布置-学生做完题 → StudentAnswer 入库
  → LLM 诊断每个错误答案的错因（线上测试）
  → barrier_type 写入学生档案（长期记忆）
  → 教师查看诊断 → 修正（如有必要）（HITL）
  → 布置针对性练习（老师操作）
  → 学生再做（反馈） → 新的练习结果入库（二次入库）
  → 诊断越来越准确（数据闭环的正反馈）
```

### 6.3 向量检索

250 道高考真题（2008-2025）通过 ChromaDB 向量化存储，支持语义检索。知识点图谱（50+ 节点）通过 JSON 组织，关联 PubChem 分子数据库。

## 九、开发方法论

### 9.1 评测先行

不是"先写代码再测试"，而是"先写评测 → 确认它失败 → 写代码让它通过 → CI 持续验证"。

- PM 写场景（"当学生问氧化还原时，Agent 应该调 redox_tutor"）
- 工程师写评测断言（先失败，因为功能还没做）
- 写实现代码（让评测通过）
- 教研顾问做化学准确性审核
- CI 门禁自动验证

### 9.2 三阶段门控

**Prototype → Pilot → Production**。每个阶段有明确的准入条件、退出标准和 kill criteria。原型阶段的核心问题是"方向对不对"，不是"功能完不完美"。

### 9.3 迭代节奏

2-4 周迭代 + 评测数据驱动的复盘。复盘不是"总结做了什么"，而是"如果重新来会怎么做"——每次复盘产出必须转化为评测场景、ADR、开发规范或 backlog item。
