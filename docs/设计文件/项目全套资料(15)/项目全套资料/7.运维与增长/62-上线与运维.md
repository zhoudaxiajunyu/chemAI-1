# 62. 上线与运维 — ChemAI

## 一、部署架构

### 1.1 整体部署拓扑

```
┌─────────────────────────────────────────────┐
│                  Docker Host                  │
│  ┌───────────────────────────┐               │
│  │  chemai (FastAPI :8000)    │               │
│  │  直接 serve 前端 + API      │               │
│  └─────────────┬─────────────┘               │
│                │                              │
│  ┌─────────────┴─────────────┐               │
│  │  Volumes                   │               │
│  │  ./data            ChromaDB + 知识图谱     │
│  │  ./chemai.db               主业务数据库    │
│  │  ./chemai_checkpoints.db   Agent 对话检查点│
│  │  ./chemai_store.db         Agent 长期记忆  │
│  │  ./logs                   应用日志         │
│  └───────────────────────────┘               │
└─────────────────────────────────────────────┘
```

### 1.2 Docker Compose 详解

```yaml
# docker-compose.yml
services:
  chemai:
    build:
      context: .
      dockerfile: Dockerfile
    image: chemai:${APP_VERSION:-latest}
    ports:
      - "${APP_PORT:-8000}:8000"
    volumes:
      - ./data:/app/data                    # ChromaDB + 知识图谱
      - ./chemai.db:/app/chemai.db          # 主数据库（WAL 模式）
      - ./chemai_checkpoints.db:/app/chemai_checkpoints.db  # Agent 对话检查点
      - ./chemai_store.db:/app/chemai_store.db  # Agent 长期记忆
      - ./logs:/app/logs                    # 应用日志
      - ./evals:/app/evals                  # 评测体系
    env_file:
      - .env
    environment:
      - APP_VERSION=${APP_VERSION:-latest}
      - PYTHONUNBUFFERED=1
    restart: unless-stopped
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:8000/api/health"]
      interval: 30s
      timeout: 10s
      retries: 3
      start_period: 40s
    ulimits:
      nofile:
        soft: 65536
        hard: 65536
```

关键设计决策：
- **单容器而非多容器**：ChemAI 面向单学校部署（同时在线 < 50 人），单体容器足够。后期可通过 `docker compose scale chemai=3` + 负载均衡横向扩展。
- **SQLite 开发环境**：零运维成本——不需要单独安装和配置数据库服务。WAL 模式支持读写并发。生产环境可迁移到 MySQL，SQLAlchemy ORM 切换连接串即可平滑过渡。
- **Volume 挂载而非 Docker Volume**：学校 IT 人员可以直接在宿主机上备份 `.db` 文件。

### 1.3 前端部署

- 开发与生产统一：前端静态文件（HTML/JS/CSS）由 FastAPI 在 8000 端口直接 serve，通过 `StaticFiles` 中间件挂载。合并为单端口，无 CORS 跨域开销，不需要独立的 Vite dev server 或 Nginx。

### 1.4 多实例部署（规模化阶段）

当单校并发超过 50 人时：
```
负载均衡器
  ├─ chemai_1:8000
  ├─ chemai_2:8000
  └─ chemai_3:8000

SQLite → 迁移至 MySQL 或 Litestream 复制
ChromaDB → 独立部署 ChromaDB Server
```

## 二、环境与配置管理

### 2.1 配置分层

| 文件 | 用途 | 敏感度 |
|------|------|--------|
| `.env` | 生产环境变量（LLM API keys、DB 路径、OCR provider） | **极高**——不入 Git |
| `.env.example` | 模板文件，不含真实 key | 低——可入 Git |
| `.env.dev` | 开发环境覆盖 | 中 |
| `app/config.py` | 统一加载 + `@lru_cache` 缓存 | 无敏感信息 |

### 2.2 关键环境变量清单

| 变量 | 说明 | 默认值 | 风险 |
|------|------|--------|------|
| `DEEPSEEK_API_KEY` | 主力 LLM provider | 无 | **泄露即产生费用** |
| `DEEPSEEK_BASE_URL` | API 端点 | `https://api.deepseek.com/v1` | 低 |
| `MIMO_API_KEY` | 小米 MiMo 备用 provider | 无 | **泄露即产生费用** |
| `DASHSCOPE_API_KEY` | 阿里通义千问 fallback | 无 | **泄露即产生费用** |
| `ZHIPU_API_KEY` | 智谱 GLM fallback | 无 | **泄露即产生费用** |
| `BAIDU_OCR_API_KEY` | 百度 OCR | 无 | 中 |
| `DATABASE_URL` | SQLite 路径 | `sqlite+aiosqlite:///./chemai.db` | 低 |
| `SECRET_KEY` | JWT 签名密钥 | 无 | **泄露可伪造任意用户身份** |
| `CHROMA_PERSIST_DIR` | 向量数据库路径 | `./data/chromadb` | 低 |
| `MINERU_ENDPOINT` | MinerU PDF 解析 | 无 | 低 |

### 2.3 配置安全实践

- **禁止**在代码中硬编码任何 key 或 secret
- `.env` 文件权限设为 `600`（仅 owner 可读写）
- 生产环境通过学校 IT 管理员手工配置，不通过自动化脚本注入
- LLM API key 支持多 provider 轮换——任意一个可用即可保证服务不中断
- `SECRET_KEY` 泄露后的应急流程：立即轮换 → 所有用户 token 失效需重新登录 → 通知学校管理员

## 三、LLM Provider 路由与容灾

ChemAI 依赖 LLM API，而国内 AI 厂商的 API 稳定性参差不齐。为此设计了一套四级 fallback 机制。

### 3.1 Provider 优先级

```python
# agent/models.py 中的路由逻辑
PROVIDER_PRIORITY = [
    ("mimo",       "moonshot-v1-8k"),       # 小米 MiMo（首选，成本最低）
    ("deepseek",   "deepseek-chat"),         # DeepSeek（主力，性价比最优）
    ("dashscope",  "qwen-turbo"),            # 通义千问（第一 fallback）
    ("zhipu",      "glm-4-flash"),           # 智谱 GLM（第二 fallback）
]
```

### 3.2 Fallback 触发条件

| 条件 | 行为 |
|------|------|
| API 返回 5xx | 立即切换下一个 provider |
| API 超时（> 30s） | 标记为"降级"，切换下一个 |
| API 返回 429（限流） | 等待 5s 重试，仍失败则切换 |
| 连续失败 3 次 | 标记该 provider 为"不可用"，15 分钟后自动重试 |
| 所有 provider 不可用 | 返回降级响应："系统繁忙，请稍后重试" |

### 3.3 成本控制

| Provider | 模型 | 输入价格 | 输出价格 | 月度预算 |
|----------|------|---------|---------|---------|
| MiMo | moonshot-v1-8k | ¥0.8/百万 token | ¥0.8/百万 token | ¥50 |
| DeepSeek | deepseek-chat | ¥1/百万 token | ¥2/百万 token | ¥100 |
| 通义千问 | qwen-turbo | ¥0.8/百万 token | ¥2/百万 token | ¥30 |
| 智谱 GLM | glm-4-flash | ¥0.1/千 token | ¥0.1/千 token | ¥20 |

实际月度 LLM 成本 < ¥200（单校部署）。成本低的秘诀：
- 大部分对话走 MiMo 和 DeepSeek
- `trim_context` 控制上下文长度（超过 30 条消息触发 LLM 摘要）
- 辅导场景缓存常见问题的工具调用结果

## 五、数据库运维

### 5.1 SQLite WAL 模式

ChemAI 使用 SQLite + WAL（Write-Ahead Logging）模式：

```python
# app/models/database.py
engine = create_async_engine(
    DATABASE_URL,
    connect_args={
        "check_same_thread": False,
        "timeout": 30,
    }
)

# 启动时执行
@listens_for(Engine, "connect")
def set_sqlite_pragma(dbapi_connection, connection_record):
    cursor = dbapi_connection.cursor()
    cursor.execute("PRAGMA journal_mode=WAL;")       # WAL 模式
    cursor.execute("PRAGMA synchronous=NORMAL;")      # 平衡安全与性能
    cursor.execute("PRAGMA foreign_keys=ON;")         # 外键约束
    cursor.execute("PRAGMA cache_size=-8000;")        # 8MB 缓存
    cursor.execute("PRAGMA busy_timeout=5000;")       # 5s 锁等待
    cursor.close()
```

### 5.2 数据库备份

```bash
# 方案一：在线备份（推荐，每天凌晨执行 cron 任务）
sqlite3 /data/chemai.db ".backup /backup/chemai_$(date +%Y%m%d).db"

# 方案二：文件拷贝（低峰期，先执行 checkpoint）
sqlite3 /data/chemai.db "PRAGMA wal_checkpoint(TRUNCATE);"
cp /data/chemai.db /backup/

# 备份保留策略
# - 最近 7 天：每日保留
# - 最近 4 周：每周保留
# - 更早的：每月保留一份
```

### 5.3 chemai_checkpoints.db 维护

Agent 对话状态持久化到此文件，会随时间增长：

| 问题 | 原因 | 解决方案 |
|------|------|---------|
| 文件持续增长 | 每次对话创建新 checkpoint | `trim_context`：超过 30 条消息触发 LLM 摘要，压缩历史 |
| 旧对话占用空间 | 学生毕业/教师离职后数据无价值 | 学期结束后归档，超过 1 年未访问的对话可删除 |
| checkpoint 碎片 | SQLite 删除后空间不回收 | 每月执行 `VACUUM` |

```bash
# 每月维护脚本
sqlite3 chemai_checkpoints.db <<EOF
DELETE FROM checkpoints WHERE updated_at < datetime('now', '-12 months');
PRAGMA optimize;
VACUUM;
EOF
```

Agent 对话状态持久化基于 LangGraph 内置后端：
- **对话检查点**：`LangGraph SqliteSaver` → `chemai_checkpoints.db`（每次 LangGraph 节点执行后自动写入检查点，保证对话中断后可恢复）
- **长期记忆**：`LangGraph AsyncSqliteStore` → `chemai_store.db`（跨会话持久化，存储学生知识掌握档案、辅导偏好等长期记忆）

### 5.4 chemai_store.db 维护

`chemai_store.db` 存储 Agent 长期记忆（学生知识掌握档案、辅导历史、偏好设置等）：

| 问题 | 原因 | 解决方案 |
|------|------|---------|
| 文件持续增长 | 每学期积累新的知识掌握数据 | 学期结束后归档，保留最近 2 个学期的活跃数据 |
| 存储冗余 | 同一知识点的多次评估记录 | 定期合并：同一学生同一知识点的旧记录用最新记录覆盖 |
| 文件碎片 | SQLite 删除后空间不回收 | 每学期末执行 `VACUUM` |

```bash
# 学期维护脚本
sqlite3 chemai_store.db "PRAGMA optimize; VACUUM;"
```

## 六、安全运维

### 6.1 网络安全

| 层面 | 措施 |
|------|------|
| 传输层 | 生产环境强制 HTTPS（FastAPI 直接 serve，uvicorn 配置 SSL 证书或用 CDN/负载均衡器终结 TLS） |
| API 层 | JWT token 鉴权，24 小时过期，支持 refresh token |
| CORS | 仅允许配置的白名单域名（`app/main.py` CORS middleware） |
| 限流 | API 级别 rate limiting（防止 API key 被盗刷） |

### 6.2 数据安全

| 数据类型 | 保护措施 |
|---------|---------|
| 学生答题记录 | 本地存储，不传校外。学生姓名脱敏（仅显示学号或匿名标识） |
| 教师账号密码 | bcrypt + salt 加密存储 |
| LLM 请求内容 | 不包含学生真实姓名，仅传递学号和题目内容 |
| JWT Secret Key | `.env` 文件 `600` 权限，定期轮换 |
| 数据库文件 | `.db` 文件权限 `600`，仅应用进程可读写 |

### 6.3 安全审计

- **M19 操作日志**：所有教师/学生的关键操作（出题、发布考试、查看诊断、修改诊断结论）记录全链路审计日志
- **登录异常检测**：同一账号短时间内多地登录 → 告警
- **API key 轮换**：LLM Provider API key 每季度轮换一次

## 八、事故响应

### 8.1 事故等级定义

| 等级 | 定义 | 示例 | 响应时间 | 修复时间 |
|------|------|------|---------|---------|
| **P0** | 服务完全不可用或数据安全事故 | 8000 端口 down、数据库损坏、Persona 隔离失效 | 5 分钟 | 1 小时 |
| **P1** | 核心功能不可用 | 学生端对话失败、教师批改管线中断、评测全红 | 15 分钟 | 4 小时 |
| **P2** | 非核心功能降级 | 家长报告推送延迟、历史数据查询慢 | 1 小时 | 24 小时 |
| **P3** | 轻微缺陷 | 前端样式异常、非关键页面报错 | 下一个迭代 | 下一个迭代 |

### 8.2 P0 事故响应 SOP

```
1. 确认事故（5 分钟内）
   ├─ 检查 healthcheck 端点状态
   ├─ 检查 Docker 容器状态：docker ps -a
   ├─ 检查磁盘空间：df -h
   └─ 检查日志：docker logs chemai --tail 100

2. 止血（15 分钟内）
   ├─ 服务 down → docker compose restart
   ├─ 磁盘满 → 清理日志 + VACUUM db
   ├─ 数据库损坏 → 从最近备份恢复
   └─ 以上无效 → 回滚到上一个稳定 Docker 镜像版本

3. 恢复服务（1 小时内）
   ├─ 验证 healthcheck 全绿
   ├─ 跑一趟确定性评测（86 个）确认功能正常
   └─ 通知种子学校教师"服务已恢复"

4. 根因分析（24 小时内）
   ├─ 写事后复盘文档（时间线 + 根因 + 改进措施）
   └─ 转化为评测场景（确保同类问题不再发生）
```

## 十、已知运维问题与解决方案

| 问题 | 现象 | 根因 | 解决方案 | 状态 |
|------|------|------|---------|------|
| 多进程僵尸占端口 | `端口 8000 已占用` 错误 | uvicorn 多 worker 模式下旧进程未正常退出 | Docker 单容器部署，避免多进程；`docker compose down` 彻底清理 | **已解决** |
| SQLite 写锁争用 | 写操作偶发 `database is locked` | 高并发写入时 SQLite 串行化限制 | WAL 模式 + `busy_timeout=5000` + 写操作排队 | **已缓解** |
| uvicorn 内存缓慢增长 | 运行 48 小时后内存 > 2GB | Python 内存碎片 + LangGraph checkpoint 缓存 | `--limit-concurrency 10` + 每周定时重启容器（周日凌晨 3:00 cron） | **已缓解** |
| DeepSeek API 临时不可用 | Agent 返回"服务暂时不可用" | DeepSeek 偶尔维护/限流 | 四级 Provider fallback 自动切换 | **已解决** |
| ChromaDB 启动遥测阻塞 | 首次启动卡住 10+ 秒 | PostHog 遥测在国内网络下超时 | 启动时设置 `ANONYMIZED_TELEMETRY=False` | **已解决** |
| `chemai_checkpoints.db` 增长 | 运行 1 个月后 > 500MB | 每次对话生成多个 checkpoint | `trim_context` 摘要 + 每月 VACUUM | **已缓解** |
| `chemai_store.db` 增长 | 多学期累积 > 300MB | 旧知识掌握数据未清理 | 学期末归档 + VACUUM | **已缓解** |
| 百度 OCR 偶发超时 | 上传答题卡后处理失败 | OCR API 单次调用超时 30s | 添加 3 次重试 + 指数退避 | **已解决** |

## 十三、vibe-coded 项目的运维特殊之处

AI 生成的代码有传统运维不覆盖的独特风险，需要额外关注：

- **LLM Provider 降级链监控**：MiMo-V2.5 → DashScope → DeepSeek 三级降级。运维需要监控每层 Provider 的调用成功率、延迟 P95、降级触发频率。某层频繁降级意味着需要更换 Provider 或优化 Prompt
- **Agent 对话状态恢复**：LangGraph 检查点（chemai_checkpoints.db）是对话连续性的生命线。定期健康检查：启动一个新对话执行预定义的操作序列，验证状态恢复正确
- **Prompt 版本回滚**：AI Coding 中 Prompt 改动就是代码变更。每次 Prompt 修改通过 Conventional Commits 记录（`git log -- agent/personas/`），Evals 基线对比保障质量不劣化。如出现退化，`git revert` 回滚 Prompt + 重新 run_evals
- **数据孤岛 vs 统一存储**：开发环境使用 SQLite 文件存储（chemai.db + chemai_checkpoints.db + chemai_store.db + chroma_db/）。生产环境统一迁移到 MySQL + 共享 ChromaDB server。迁移路径：SQLite → MySQL（SQLAlchemy 切换连接串），ChromaDB 持久化目录 → ChromaDB server（Docker 部署）
- **成本监控**：AI Coding 项目的运营成本以 LLM API 调用为主。运维需监控各 Provider 的月调用量、Token 消耗、成本趋势。当成本超过阈值（如 >500 元/月），触发 Provider 策略调整（如默认 Provider 从 MiMo 切换到 DeepSeek）
