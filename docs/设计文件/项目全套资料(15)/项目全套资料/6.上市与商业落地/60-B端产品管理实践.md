# 60. B端产品管理实践 — ChemAI 的干系人管理与团队协作

> ChemAI 面向学校/教育局，是典型的 B2B2C（学校采购→教师使用→学生受益→家长感知）模式。本文档总结 ChemAI 在 B 端产品管理中的实践经验，覆盖干系人管理、采购流程、定价策略、团队协作和 AI 产品的特殊性。

---

## 一、B端 vs C端：AI 教育产品的结构性差异

ChemAI 面向学校而非个人消费者，这决定了产品管理的底层逻辑与 C 端产品完全不同。

| 维度 | C 端产品 | B 端产品（ChemAI） |
|------|---------|-------------------|
| **决策者** | 使用者自己 | 校长/教研组长（决策者）≠ 一线教师（使用者）≠ 学生（受益者） |
| **采购周期** | 即时决策（几分钟） | 3-6 个月（演示→试用→评估→预算审批→招投标→签约） |
| **评估标准** | "好不好用" | "学生成绩有没有提升"（续费靠效果数据） |
| **付费意愿** | 个人冲动消费 | 预算制，需要 ROI 论证 |
| **切换成本** | 低（卸载重装） | 极高（教师已嵌入工作流，数据已积累一学期） |
| **数据合规** | 隐私政策勾选 | 红线——等保认证、数据本地化、家长知情同意 |
| **产品迭代** | 快速试错，A/B test | 学期节奏，寒暑假窗口期 |
| **推广方式** | 应用商店/广告/裂变 | 教研会议/教育局推荐/种子校转介绍 |

### 1.1 三重角色撕裂：最容易被忽视的 B 端陷阱

ChemAI 的产品设计需要同时服务三组需求完全不同的人：

```
决策者（校长/电教主任）
  "这东西能提升升学率吗？多少钱？部署麻烦吗？"
  关注：ROI、数据安全、竞品对比、政策合规

        ↓ 采购决策

使用者（化学老师）
  "能帮我省多少时间？诊断准不准？操作复不复杂？"
  关注：批改速度、诊断准确性、培训成本

        ↓ 日常使用

受益者（学生 + 家长）
  "我的错题被理解了吗？我该怎么改进？"
  关注：错题解析质量、练习推荐精准度、进步可视化
```

**核心矛盾**：决策者感受不到使用者的痛点，使用者没有采购权，受益者无法直接反馈。PM 的工作就是在这三角中找到平衡——让决策者看到"投入产出比"，让使用者感到"省时间"，让受益者看到"进步"。

## 二、干系人地图

### 2.1 四层干系人矩阵

| 层级 | 角色 | 核心关注点 | 沟通频率 | 沟通方式 | 关键信息 |
|------|------|-----------|---------|---------|---------|
| **决策层** | 校长/副校长 | 升学率提升、学校竞争力、与竞品学校差距 | 季度 | 数据报告 + 案例展示 + 对比分析 | "使用 ChemAI 的学校化学平均分提升 X 分" |
| **决策层** | 电教主任 | 部署复杂度、数据安全、与现有系统集成 | 月度 | 技术白皮书 + 部署方案 | "单容器部署，10 分钟上线，兼容钉钉/企业微信" |
| **管理层** | 教研组长/年级主任 | 教师工作量减少、教研数据可用性、备课效率 | 月度 | 班级热力图 + 教研数据导出 | "全年级化学薄弱知识点一键诊断" |
| **管理层** | 教务主任 | 排课影响、考试流程嵌入、教师培训安排 | 按需 | 流程对接文档 | "不改变现有考试流程，拍照即可" |
| **使用层** | 一线化学教师 | 操作简单、省时间、诊断准确、学生认可 | 周度 | 微信群 + 培训 + 反馈收集 | "批改时间从 6h → 45min" |
| **间接层** | 家长 | 孩子学习状态、进步趋势、不需要懂化学 | 月度 | 家长端学情周报 | "非分数、非排名、纯诊断信息" |
| **间接层** | 学生 | 错题被理解、练习有针对性、操作不繁琐 | 日常 | 学生端 AI 对话 + 练习 | "引导式对话，不给答案" |

### 2.2 干系人权力/兴趣矩阵

```
        高权力
          │
  ㊟ 校长     │  ㊟ 教研组长
  ㊟ 电教主任  │  ㊟ 一线教师 ★核心
  (满足需求)  │  (紧密合作)
          │
  ─────────┼────────── 高兴趣
          │
  ㊟ 教务主任  │  ㊟ 家长
  (保持知情)  │  ㊟ 学生
          │  (保持沟通)
          │
        低权力
```

**策略重点**：教研组长和一线教师位于"高权力+高兴趣"象限，是驱动采购和续费的核心力量。PM 的精力分配应为：教师体验 50% > 教研组长关系 25% > 校长汇报 15% > 家长/学生 10%。

## 三、B端销售与采购流程

### 3.1 典型采购路径

```
┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐
│ 1. 触达   │→  │ 2. 演示   │→  │ 3. 试用   │→  │ 4. 评估   │→  │ 5. 采购   │
│ 教研会议  │   │ 给教研组长 │   │ 1-2个班级 │   │ 对比数据  │   │ 预算/招标 │
│ 种子校推荐 │   │ 20min场景  │   │ 2周深度用 │   │ ROI论证  │   │ 合同/付款 │
└──────────┘   └──────────┘   └──────────┘   └──────────┘   └──────────┘
                                                      ↓
                                               ┌──────────┐
                                               │ 6. 续费   │
                                               │ 学期末评估 │
                                               │ 效果数据驱动 │
                                               └──────────┘
```

### 3.2 各阶段关键动作

**阶段 1：触达**
- 最有效渠道：省级化学教研活动、学科会议（种子教师现场证言 > 任何广告）
- 种子学校转介绍是最高 ROI 渠道——湖南省化学教研圈子里，3 所种子校的教研组长可以在一个学期内触达 20+ 所学校
- 不要等产品完美再推广——种子期产品的"不完美"反而是建立深度合作关系的契机（教师在试用期提出的建议被采纳 → 忠诚度远超买现成产品的用户）

**阶段 2：演示**
- **核心原则：演示的不是功能，是场景。** 教研组长想看的东西不是"我们有 22 个 AI 工具"，而是"你帮我解决什么事情"
- 准备的标准 demo 脚本："一位老师收上来 30 张答题卡 → 拍照上传 → 3 分钟自动批改 → 每人一份诊断报告 → 班级薄弱知识点 TOP5 → 针对性推送练习题"
- demo 全程控制在 20 分钟内（15 分钟场景演示 + 5 分钟 Q&A）
- **禁止**在 demo 中展示技术架构、Agent 概念、评测体系——教师不关心这些
- **必须**展示两个"Wow Moment"：① 化学方程式配平零误差（任何方程都能秒配）② 错因诊断具体到"审题错误：未注意反应条件"

**阶段 3：试用**
- 试用期的 KPI 提前约定：不要等到试用结束后讨论效果。"我们看三个指标：① 教师批改时间是否减少 50% 以上 ② 诊断结论被教师认可率（修正率 < 20%）③ 学生练习完成率 > 70%"
- 试用配置：1-2 个班级、2 周时间、3 位老师参与
- **第一周是生死线**：老师在第一周如果没有体验到"省时间"的价值，第二周就不会用了。确保第一天就完成一次完整流程（出题→发布→学生作答→批改→诊断报告），让老师在 24 小时内感受到核心价值
- 培训不是可选项：准备 20 分钟录屏教程、一个 FAQ 文档、一个答疑微信群

**阶段 4：评估**
- 输出试用报告：对比试用班和对照班的核心指标
- 关键数据点：教师批改时间变化（6h → 45min）、诊断采纳率（82%）、学生练习完成率、知识点掌握率变化
- 同时收集定性反馈："张老师说以前考完试要加班一整个周末批改，现在周五下班前就能出报告"

**阶段 5：采购**
- 公立学校采购路径：教研组提出需求 → 教务处审核 → 校长办公会审批 → 招投标或询价采购 → 签订合同
- 关键节点：预算周期（学校通常在年末做下一年预算，错过窗口就是半年等待）
- 定价弹性：学校预算不同，可以提供"基础版（批改+诊断）"和"完整版（+自适应练习+家长端）"两档选择

**阶段 6：续费**
- 续费决定在学期末做出——前面 4 个月的日常使用数据决定了续费率
- 续费会议需要准备：本学期使用数据总结 + 新学期功能规划 + 续费优惠方案
- 流失预警信号：周活跃率连续下降 4 周、教师不再新建考试、诊断报告的修正率突然升高

### 3.3 定价策略

| 方案 | 内容 | 年费 | 适用对象 |
|------|------|------|---------|
| **基础版** | 答题卡 OCR 批改 + 错因诊断 + 班级学情面板 | ¥3,000/班/年 | 预算有限的普通高中 |
| **标准版**（推荐） | 基础版 + 自适应练习 + 学生端 AI 辅导 + 家长周报 | ¥5,000/班/年 | 重点高中 |
| **完整版** | 标准版 + 真题关联 + 教研数据导出 + 专属教研顾问 | ¥8,000/班/年 | 省示范性高中/教研需求 |
| **区域版** | 覆盖全区/县所有高中化学学科 + 区域教研数据平台 | ¥10-50 万/区/年 | 教育局统一采购 |

**定价依据**：
- 一个化学老师的时间成本 ≈ ¥50-100/小时（含工资+福利）。ChemAI 每周节省 5-10 小时，年化节省 ¥12,000-48,000
- 对比校外辅导（200-500 元/课时 × 40 周 = ¥8,000-20,000/年/生），ChemAI 摊到每个学生仅 ¥60-160/年
- **竞品价格锚点**：学科网/组卷网全套资源+组卷服务约 ¥22,000-30,000/校/年（莆田华侨中学、蚌埠二中 2024 年真实招标数据）；NOBOOK 虚拟实验室学校版约 ¥400/套（湖北樊城 2024 年捐赠 498 套总值约 20 万）。ChemAI 单学科深度工具的定位，¥3,000-8,000/班/年的价格带处于合理区间
- **行业基准**：EdTech B2B LTV/CAC 黄金标准为 3:1（First Page Sage 2023；Chargebee 2024 SaaS 基准）。ChemAI 种子期 LTV/CAC 理论值约 9:1（6 班 × ¥5,000 × 3 年 = ¥9 万 LTV vs ¥10,000 CAC），属偏乐观假设，待实际销售数据验证
- **采购模式参考**：教育信息化项目推荐"3331"支付节奏（签约 30% + 到货 30% + 上线稳定 30% + 运维尾款 10%），招标技术/商务分 60-70%、价格分 30-40%

## 四、内部团队协作

### 4.1 角色配置

```
产品经理（PM）
  │
  ├── 化学教研顾问（1 人，兼职）
  │   职责：知识点体系维护、题目审核、评测数据标注、教师反馈解读
  │   背景：退休高中化学特级教师或有 10+ 年教学经验的教研员
  │
  ├── AI 工程师（1 人）
  │   职责：Agent 架构设计、Tool 开发、Prompt 工程、评测体系维护
  │   背景：熟悉 LangGraph/LangChain，有 LLM 应用开发经验
  │
  ├── 全栈工程师（1 人）
  │   职责：FastAPI 后端、前端（React + Vite）、数据库、部署
  │   背景：Python + JavaScript，熟悉 Docker
  │
  └── QA/评测工程师（PM 兼任，种子期）
      职责：Evals 维护、回归测试、评测报告分析
      背景：中期可独立招聘
```

**种子期团队规模：3 人（PM + AI 工程师 + 全栈工程师）+ 1 兼职教研顾问。** 小而精的团队更适合 AI 产品的 0→1 阶段——沟通成本低、决策速度快、每个人都理解产品的全貌。

### 4.2 协作节奏

| 节奏 | 活动 | 参与人 | 时长 | 产出 |
|------|------|--------|------|------|
| **每日** | 站会 | 全体 | 10 min | 阻塞识别 |
| **每周一** | 需求评审 | PM + 工程师 | 1h | 本周优先级排序 |
| **每周三** | 评测 review | PM + AI 工程师 + 教研顾问 | 30 min | 评测场景审核 |
| **每周五** | Demo + 评测报告 | 全体 | 1h | 评测通过率 + 功能展示 |
| **每迭代末** | 复盘 | 全体 | 1.5h | 改进措施 + 下迭代计划 |

### 4.3 评測先行的协作模式

ChemAI 采用"评测先行"而非"需求先行"的协作模式。这与传统软件开发有本质区别：

**传统模式**：
```
PM 写需求文档 → 工程师写代码 → QA 测试 → 上线 → 用户发现问题
```

**评測先行模式**：
```
PM 写评测场景 → 工程师建评测（先失败）→ 写代码让评测通过 → 全量评测 → 通过即上线
```

为什么必须评测先行？
- Agent 的行为不是确定性的——同一个 Prompt，LLM 两次回复可能不同
- PM 口头描述的"Agent 应该怎么表现"无法验证——"当学生问氧化还原反应时，Agent 应该调 redox_tutor"这句话，只有写成评测断言才能自动化验证
- 评测是 PM、工程师、教研顾问三方共识的载体——PM 写场景（从用户角度），工程师写断言（从实现角度），教研顾问审核（从化学准确性角度）

### 4.4 需求管理：AI 产品不能用传统方式

传统产品需求："按钮颜色改为蓝色，字号 14px"
AI 产品需求："当学生说'我不会这道题'时，Agent 应该反问'你卡在哪一步了'而不是直接给出答案"

| 传统需求 | AI 产品需求（Agent 行为约束） |
|---------|--------------------------|
| UI 变化可截图确认 | 行为变化需评测验证 |
| 改一行 CSS 就完成 | 改 Prompt + 调 docstring + 跑评测 |
| 回归测试看 UI 截图 | 回归测试看工具调用轨迹 |
| "这个功能做完了" | "对应 3 个评测场景 100% 通过" |

### 4.5 与教研顾问的协作

教研顾问是 ChemAI 区别于通用 AI 产品的核心差异化角色。协作要点：

- **题目审核**：AI 生成的每道化学题都需要教研顾问确认"这道题在高考范围内、答案正确、难度合理"
- **评测数据标注**：障碍诊断的 ground truth 由教研顾问标注——"这个学生的错误是概念障碍还是审题障碍？"——这个判断 AI 做不了
- **反馈翻译**：教师说的"这个诊断不对"，教研顾问要翻译成"诊断引擎对'离子方程式拆分'场景的 barrier_type 判断逻辑需要调整"
- **时间投入**：种子期 5-8 小时/周，推广期 10-15 小时/周

## 五、PM 在 AI 产品中的核心能力

在 ChemAI 这个项目中，PM 的角色不是传统意义上的"提需求"。需求来自教师反馈和 evals 数据。PM 的真正角色是：

### 5.1 定义行为标准

当学生说"帮我配平 Fe + O2 = Fe2O3"时，Agent 应该做什么？PM 需要把"应该做什么"写清楚：

```
Scenario: 学生请求配平
  Input: "帮我配平 Fe + O2 = Fe2O3"
  Expected:
    - Agent 必须调用 balance_equation 工具
    - Agent 不得直接文字回复配平结果
    - Agent 不得调用 chemistry_tutor（这是配平不是辅导）
    - 配平结果必须包含"配平步骤"而不只是最终系数
  Verification:
    - evals assert: tool_called == "balance_equation"
    - evals assert: response contains "步骤"
```

这不是"需求文档"，这是"行为标准"——PM 定义，工程师实现，教研顾问审核，evals 验证。

### 5.2 管理评测阈值

不是所有指标都要 100%。PM 需要根据产品阶段和风险等级设定合理的阈值：

| 评测维度 | 当前阈值 | 告警阈值 | 阻断阈值 | 理由 |
|---------|---------|---------|---------|------|
| Persona 隔离（安全层） | 100% | 99% | < 100% | 学生不能看到教师工具——底线不容妥协 |
| 路由准确性 | 85% | 80-85% | < 75% | LLM 的非确定性意味着不可能 100% 完美，85% 是经验上"基本可靠"的线 |
| 工具调用准确性 | 90% | 85-90% | < 85% | 调对工具是执行正确操作的前提 |
| 工作流完整性 | 85% | 80-85% | < 80% | 多步骤任务中的单步失败可以容忍 |
| 性能 P95 | 3s | 3-5s | > 5s | 3 秒是"不打断用户心流"的阈值 |

PM 的工作不是盯着每个指标看，而是在团队争论"这个 bug 要不要今天修"时，根据评测阈值做判断——"路由准确率跌到 80% 了，到了告警线但还没到阻断线。今天先不管，列入下周迭代计划。"

### 5.3 驱动数据闭环

教师的每一次"修正诊断"都是训练信号。PM 要确保这个信号能回流到产品改进中：

```
教师修正诊断 "这个学生不是概念障碍，是审题障碍"
  → PM 标记为"诊断不一致案例"
  → 教研顾问分析原因（Prompt 问题？规则引擎逻辑问题？）
  → 工程师调整
  → 新增 evals 场景
  → 跑评测确认修好了
  → 下次同样的题型不会再误判
```

### 5.4 翻译技术语言

AI 工程师说的和教师能理解的之间，需要 PM 做翻译：

| 工程师说 | PM 翻译给教师 | PM 翻译给校长 |
|---------|-------------|-------------|

## 六、常见的坑与应对

### 6.1 产品层面

| 坑 | 为什么危险 | ChemAI 的应对 |
|----|---------|-------------|
| **把模型能力当产品能力** | DeepSeek 能配平方程式 ≠ "产品能配平"。产品的能力是端到端流程 | 所有 demo 和评估都基于"拍照→批改→诊断报告"完整流程，不单独展示 LLM 能力 |
| **过早追求功能广度** | 学校采购看的是"化学诊断准不准"，不是"有没有 100 个功能" | 种子期聚焦 F1 OCR + F4 诊断两个核心闭环，其余所有功能都在这个闭环上延伸 |
| **忽略教师培训投入** | AI 工具的 adoption 瓶颈往往不是功能不够，而是老师不会用 | 20 分钟录屏教程 + FAQ + 答疑微信群 + 前两周日活盯盘 |
| **学期节奏搞错** | 期末考试前一周上线新功能 = 没人用。期中考试后一周 = 最佳窗口 | 重大功能上线对齐学校考试日历 |
| **等产品完美再上线** | 办公室里闭门造车的"完美产品"，上线第一天就遇到你没想到的使用场景 | v0 只有配平+基本对话，但上线就能收集真实反馈 |

### 6.2 技术层面

| 坑 | 为什么危险 | ChemAI 的应对 |
|----|---------|-------------|
| **Prompt 退化** | LLM 提供方悄悄升级模型 → 行为改变 → 评测不通过 → 没人知道为什么 | CI 定时跑全套评测，任何维度下降 > 5% 触发告警 |
| **成本失控** | "再加一个 tool 就要多调一次 LLM" × 1000 次/天 = 账单爆炸 | 每个 tool 评估"是否真的需要 LLM round-trip"，能用规则引擎的不用 LLM |
| **评测成为摆设** | 评测写了但没人维护 → 失效的评测给人虚假的安全感 | 评测覆盖诚实原则：未触发的场景报告为 null，不是 100% |

### 6.3 组织层面

| 坑 | 为什么危险 | ChemAI 的应对 |
|----|---------|-------------|
| **教研顾问成为瓶颈** | 所有题目和诊断都要教研顾问审核 → 开发速度被拖慢 | 优先建立审核标准（什么情况可以自动通过），目标是 80% 的题目不需要人工审核 |
| **PM 变成传话筒** | 教师说"诊断不对"→ PM 转述给工程师 → 工程师说"Prompt 改了"→ PM 转述给教师 | PM 必须理解 Agent 的工作原理到可以独立判断"这个反馈是 Prompt 问题还是模型选择问题"的程度 |

## 八、AI 产品的 B 端管理特殊性

vibe-coded 项目在 B 端场景下有几个传统产品管理不需要面对的挑战：
- **版本节奏**：传统软件有固定的发版窗口（寒暑假）。AI Coding 的版本迭代可以 2-3 天一次。但 B 端客户不需要这种速度——他们需要稳定。策略：内部保持高速迭代（`/ship` 周发），对外按学期节奏发布稳定版（`git tag v1.0.0`）
- **客户演示**：B 端演示中客户会提出"能不能加个 X 功能"。传统回复是"下个版本"。AI Coding 的回复是 `/investigate` 分析可行性 → `/opsx:propose` 快速提案 → 下次演示（可能就在下周）就能展示原型
- **合规审查**：AI 生成内容（出题、诊断）需要可审计。第五部分的 Evals 评测体系 + Golden 数据集 + 基线对比，为每一份 AI 输出提供可追溯的质量记录
- **技术债务**：vibe coding 的速度以技术债务为代价。B 端场景不可接受。第五部分的 TDD（每模块 pytest）+ Evals（每次合并基线对比）构成的'安全网'是底线——没有这两层，不可向客户交付
